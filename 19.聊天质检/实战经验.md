# 聊天质检实战经验

## 1. 本项目真正要解决什么

不是“把网页打开”或“抓到一段文本”，而是：

> 从后台真实售前会话中，保留完整上下文，用可复核证据判断客服是否热情、主动跟单、积极解决问题。

因此流程必须是：后台取最新数据 → 保存标准记录 → AI亲自通读完整会话 → 先向用户汇报店铺和客户ID → 与用户确认反馈内容、客服对象和是否发送 → 生成预览；只有用户给出明确确认口令后才发送。

## 2. 为什么之前会打开到现有 Edge

普通 Edge 已经有自己的主进程。再次执行 `start` 或直接打开 URL，Windows/Edge 往往把请求转发给现有进程；即使命令行写了 `--remote-debugging-port`，现有进程也不会因此变成调试浏览器。

表现通常是：

- 页面能打开，但 9333 没有监听；
- 出现一个 Edge 默认页或恢复页，加上目标后台页；
- 程序无法通过 `/json/list` 看到页面。

## 3. 已验证的独立浏览器做法

9号项目采用的关键做法已迁移到本项目：

1. 为项目使用专用端口 9333，不抢普通 Edge 常用端口 9222；
2. 使用项目自己的 `runtime/browser-profile/`，不复用当前 Edge 资料目录；
3. 使用 Node `child_process.spawn`，`detached: true`、`stdio: 'ignore'`，直接启动可见浏览器；
4. 使用 `--no-first-run`、`--no-default-browser-check`、`--hide-crash-restore-bubble`、`--disable-session-crashed-bubble`；
5. 不使用 `--restore-last-session`，避免恢复旧标签页和旧会话；
6. 启动前检查端口，端口被占用时报告，不擅自结束未知进程；
7. 通过浏览器页面内的 `fetch(..., { credentials: 'include' })` 调京东接口，复用用户手工登录 Cookie；
8. 本机 CDP 请求加入 `NO_PROXY`，避免代理误处理 `127.0.0.1`。

## 4. 正确操作顺序

### 4.1 拉起独立浏览器

```powershell
node src/cli.js browser:start
```

看到独立 Edge 后，用户自己完成登录、验证码和安全验证，并回到：

```text
https://shop.jd.com/jdm/kefu/kf-manage-lite/#/UtilsSetting/ChatLog
```

### 4.2 先列出会话，不要直接猜一条

```powershell
node src/cli.js fetch:list --start 2026-09-09
```

程序会按“京东客服管家”标题或 `kf.jd.com` URL 找目标页；空白页、Edge 新建标签页会被忽略。`fetch:list` 默认只列岗位为“售前”的会话；如确需抽查售后，必须显式使用 `--role 售后` 或 `--role all`。

### 4.3 保存指定会话

```powershell
node src/cli.js fetch:save <sid> --start 2026-09-09
```

保存后的标准格式是：

```json
{
  "format": "chat-record/1",
  "meta": { "customer": "脱敏ID", "window": "YYYY-MM-DD", "store": "" },
  "messages": [
    { "time": "...", "role": "customer", "text": "..." },
    { "time": "...", "role": "waiter", "text": "..." }
  ]
}
```

### 4.4 人工通读并质检

程序不提取响应时延、关键词、连续消息或“热情/跟单”信号。最终判断必须由 AI 亲自回看完整聊天：

- 热情：有没有承接情绪、礼貌回应、让客户感到被认真对待；
- 主动跟单：有没有追问有效需求、主动提供下一步、客户没继续问时仍有效推进；
- 积极解决：有没有查库存、算价格、申请优惠、给替代方案等具体动作。

### 4.5 反馈前后顺序

给用户反馈时，先交代：店铺名称、客户 ID、客服后台昵称和对应客服姓名，再给出逐条证据和建议。用户确认文案后，先用预览工具核对目标客服和@方式，最后才讨论是否发送。

本次真实验证的关键结果：京东记录中的后台昵称可以通过9号项目映射到 canonical 客服；1号项目当前没有配置 userid，因此使用手机号底部@；用户确认后发送返回企微 `errcode=0`。

## 5. 当前质检口径

### 热情

证据重点：

- 是否先回应客户感受，而不是直接甩结论；
- 语气是否完整、自然、愿意帮助；
- 是否出现明显冷处理、敷衍或机械重复。

不能只因为出现“您好”就判定热情，也不能只因为出现“哦”就判定冷淡，要结合上下文。

### 主动跟单

有效主动跟单通常包括：

- 追问规格、数量、预算、使用场景等关键需求；
- 主动核价、查库存、给链接或提供方案；
- 客户表达犹豫后，主动给出下一步选择；
- 客户暂时没有追问时，补充有价值的信息并推动决策。

连续发两条消息只是“主动信号”，如果只是重复“现在就是这个价格”，不能算有效跟单。

### 积极解决

重点看是否把问题向前推进：

- 只解释现状：积极性偏弱；
- 解释后给出可执行方案：积极性较好；
- 给方案并确认客户下一步：积极性更强。

## 6. 不允许的做法

- 不用旧的 `runtime/chat` 记录冒充今天后台最新数据；
- 不因为一条会话就评价整个客服；
- 不把响应快直接等同于热情；
- 不把优惠直接等同于主动跟单；
- 不把关键词统计直接等同于 AI/主管结论；
- 不把客户 ID、姓名、Cookie、密码写入源码或文档；
- 不擅自杀掉未知端口进程，尤其不要结束用户现有浏览器。

## 7. 企业微信反馈工具

### 7.1 1号项目的实际机制

1号项目的通知链已只读复核：

- 正文优先使用企微官方 `<@userid>` 行内艾特；
- 没有 userid 时，把手机号放入 `mentioned_mobile_list` 做底部@；
- webhook 请求体是 `msgtype: "text"` + `text.content` + `mentioned_mobile_list`；
- 发送有超时和一次重试。

岗位映射也必须保留：1号从成员接口的显示名中解析“姓名 + 售前/售后”，9号的 `personMappings` 保存“后台昵称 → 汇总姓名 → 岗位”。19号把两者合并到 `nicknameMappings`，选取会话时默认只允许“售前”，不能把“小洛→陈燕玲（售后）”当成售前样本。

19号复刻为 `src/services/wecomFeedback.js`：客服昵称来自9号项目映射，企微成员目录来自1号项目；`wecom:preview` 只构造预览，不联网。

多行反馈建议使用：

```powershell
node src/cli.js wecom:preview <聊天文件名> --content-file <文案文件>
```

代码调用时使用 `contentLines` 或 `joinFeedbackLines()`，不要在多层命令字符串里手写转义换行。

### 7.2 发送边界

- 反馈原文必须由用户与 AI/人工先沟通确定；本项目不自动生成评价。
- 是否发送必须由用户明确决定；当前 CLI 不提供自动发送命令。
- 底层发送函数要求明确确认口令；本次已在用户确认后成功发送一次，未确认时测试证明不会触发网络请求。

### 7.3 换行踩坑

1号项目的 `buildTransferReminderMessage()` 使用 `lines.join("\n")` 生成真实换行，`wecomRobot.js` 直接把 `input.content` 放入 JSON 请求体。`JSON.stringify()` 在调试输出里显示 `\n` 是正常的 JSON 表示；如果群里显示的是字面量 `\n`，说明发送前的字符串本身就包含反斜杠和字母 n。

本次曾因 PowerShell → Node → JavaScript 多层转义，多转义了一层，导致群里出现字面量 `\n`。以后按以下规则执行：

- 多行文案优先写文件，用 `--content-file` 读取；
- 程序内部用 `lines.join("\n")` 或 `joinFeedbackLines()`；
- 不把 `\\n` 当作最终文案内容传给 webhook；
- 发送前预览应检查字符串含真实换行，而不是只看 JSON 打印结果。

### 7.4 两种@方式不能混用

- `bottom-mobile`：正文不写客服@，只把手机号放入 `mentioned_mobile_list`，企业微信会自动在消息底部显示@。
- `inline-userid`：正文使用 `<@userid>`，`mentioned_mobile_list` 保持为空。
- 两种方式不能同时写；19号工具现在会拒绝“底部手机号@ + 正文客服@”，防止重复艾特。

本次正确模板是：

```text
【店铺】
客户ID：<客户ID>
【售前跟进建议】……
```

审批给用户看的正文也按这个模板展示，不额外添加 `@客服姓名` 行；真正的@由发送层根据映射完成。只有切换到行内 userid@时，才在正文中出现 `<@userid>`。

## 9. 后续扩展顺序

1. 先稳定真实取数和人工抽查；
2. 再积累不同售前场景样本；
3. 再让 AI 按固定证据格式输出质检结论；
4. 最后才考虑汇总到客服维度，且必须保留样本量和原始证据。
