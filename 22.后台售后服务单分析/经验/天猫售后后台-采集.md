# 天猫售后后台：怎么采集（2026-09-18 实测）

## 一、入口与登录态
- 后台地址：`https://qn.taobao.com/home.htm/trade-platform/refund-list`（页面标题「退款管理」）
- 登录态：**复用 9号 天猫店铺 profile**（9号 每天在跑，Cookies 一直新鲜）。
  做法：把 `9.客服数据自动更新/runtime/state/browser-profiles/store-chrome-profiles/tmall/<店>/account-*/`
  整个目录拷进本项目 `runtime/state/browser-profiles/tmall/<店>/`，即带着登录态，**不需要重新登录**。
  实测 2026-09-18 13:56 拷贝后直接打开就是登录态（页面显示 德达旗舰店 / 小黛 / 客服主管）。
- 窗口常驻：一个店铺一个 profile + 一个固定调试端口（`project-config/stores.json`：tmall1=9421、tmall2=9422），
  窗口开着就一直复用，登录态也在 profile 里。

## 二、数据是「服务端渲染」，不需要逆向接口
- 列表数据直接在 HTTP 文档/DOM 里（HTML 里就有「售后单号 … / 申请时间 … / 买家退货 已签收 / 退款待处理」）。
- 页面确实会发 mtop 接口，但**都不是列表数据源**（实测抓到的是辅助接口）：
  - `mtop.alibaba.refundface2.disputeservice.qianniu.pc.listversion`（列表版本号）
  - `...pc.statistic`（看板统计） `...pc.indecator`（售后体验指标） `...pc.deliverlist`（表单项配置）
  - `...pc.viewlogistic`（看物流）
  - 且这些响应里很多字段是**类型占位符**（`"str"/"bool"/"dict"`），别拿它们当数据用。
- 真正可用的采集方式是 **读 DOM**：用 `src/tools/dump-table.js`（把表格行原样结构化搬回来）。

## 三、列表结构（实测）
- 顶部看板（实时，统计更新时间就是刚才）：待处理售后 全部 9 / 24小时内待处理 0 / 退款待处理 1 / 待收货 8 / 待举证 0；
  需关注售后：小二已介入 0 / 商家已拒绝 1 / 超时同意退款 0 / 买家催促退款 0 / 待买家处理 2。
- 下方「售后单查询」：`全部售后 / 退款（不含退货） / 未发货退款 / 未收货退款 / 待收货退款 / 退货退款 / 退运费 / 换货 …` 标签 + 申请时间筛选 + 批量操作。
- **表格里每个售后单占 2 行**（第 1 行是单据信息，第 2 行是商品/金额/原因/物流/按钮），抓行时要成对处理。
- 第 1 行字段（实测片段）：
  `售后单号 407319804404762740 | 订单编号 5127667812586099609 | 申请时间 2026-09-12 09:59:24 | 退货退款 | 买家昵称(脱敏 g**)`
- 第 2 行字段：商品标题、规格、商家编码、商品ID、**买家实付 ￥498.00**、**退款总额 ￥498.00**、原因（如 不想要了/七天无理由）、件数、物流状态（如 **买家退货 已签收**）。
- **判"漏处理"要用的关键字段 = 订单编号（主订单号）+ 申请时间 + 当前状态 + 物流状态**。

## 四、还没测清（下次接着做）
- 「全部 9 条」怎么一次性拿全：默认视图只渲染出 2 行（可能只渲染首屏/需要切标签或翻页），
  卡片点击（如「全部」）用文本匹配没点到 —— 下次改用更精确的选择器 / 直接点卡片元素。
- 是否有「导出」按钮能一次导出 Excel（页面上出现过「导出」文字，未验证）。
- 多店铺：账号可在店铺间切换，**核对前必须先确认当前店铺名**（页面右侧显示店名），否则会把 A 店数据算到 B 店。

## 五、概览数字直接读（2026-09-18 用户发现，实测可用）
售后后台列表页顶部「售后单统计」有一排数字，**不用一个个开详情**：
`待处理售后 全部 9 ｜ 24小时内待处理 0 ｜ 退款待处理 1 ｜ 待收货 8 ｜ 待举证 0 ｜ 需关注售后(小二已介入/商家已拒绝/超时同意退款/买家催促退款/待买家处理) …`

**为什么这排数字就能判漏**：天猫规则是「退件显示签收/拒收后，剩余处理时长缩短为 48 小时」，
于是 **剩余 ≤ 24h ⟺ 签收已超 24h**。所以
- **「24小时内待处理 = 0」⟹ 没有"签收超 24h 还没处理"的单 = 没漏**（漏 ⊂ 签收超24h）；
- 若 >0，再点「24小时内即将超时」筛选看是哪些单，然后查金山是否已登记。

工具：`node src/tools/tmall-refund-overview.js [--store tmall1|tmall2] [--probe-pending]`
实测 2026-09-18 15:56 tmall1：24小时内待处理 0 ｜ 待处理售后 9 ｜ 退款待处理 1 ｜ 待收货 8 ｜ 待举证 0 ｜ 待买家处理 1
（与用户后台截图逐项一致）。

## 六、抓页面时的两个硬坑（2026-09-18 实测）
1. **必须每单新开标签页**：淘宝后台是 SPA，复用同一标签页 `page.goto()` 到别的详情页**页面不响应**
   （连抓 10 次拿到同一单内容）→ 工具 `tmall-refund-probe.js` 改成每单 `context.newPage()`。
2. **innerText 里标签与数字是换行分隔**（`24小时内待处理
0`）→ 提取数字要按标签位置往后找第一个数字，
   正则里若写了 `[^0-9
]` 会永远匹配不到。
