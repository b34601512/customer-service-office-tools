# 经验包：Git Bash 的六个坑（nul／反引号／中文变量／tmp／heredoc／路径转换）

> **一句话**：Windows 上的「Git Bash」是 MSYS 套出来的一层壳，处处和 Windows 两套理解打架：
> 命令行的转义、路径映射、设备名、变量名都可能悄悄咬你一口。这里按坑打包，附现场复现与清理工具。
>
> 用法：把本文件夹交给你的 AI，说「照这个包，把我脚本里的 Git Bash 坑排一遍」。

---

## 一、`> nul` 会真建一个删不动的文件

- **现象**：在 Git Bash 里想「屏掉输出」写了 `2>nul`——结果建出一个**名为 `nul` 的文件**（`git status` 里明晃晃一个 `??`）。
- **根因**：`nul` 是 cmd/PowerShell 的空设备；bash 不认，老老实实建了个文件。
- **对策**：
  1. 屏输出一律 `> /dev/null 2>&1`（别用 `nul`）；
  2. 已经建出来了：**先备份内容，再用 `\\?\` 长路径前缀删**（`模板\清保留名文件.py`，不硬丢内容）；
  3. 顺手体检仓库里有没有 `con/aux/prn/com1/lpt1` 这类保留名文件。
- **坑中坑**：拼 `\\?\` 路径时**别对 `nul` 本身调 abspath**——Windows 会给成 `\\.\nul`（设备路径），
  加了前缀反而打不开；要对「目录」取绝对路径再拼文件名（本包脚本已按此写）。

## 二、反引号 / `$` / `!`——双引号里照样被吃

- **现象**：给消息正文里的路径加了反引号 → bash 报 `command not found`，**消息却照样发出去了**，那段变空括号；
  或在 `python -c "…replace('…`档案`…')"` 里直接 `unexpected EOF`。
- **根因**：反引号在**双引号里也是命令替换**；`$` 是变量替换、`!` 是历史展开，同类。
- **对策**：正文里有这些字符 → 用**单引号**包整个参数；长文本写成文件再传；
  非用 heredoc 就用**带引号**的 `<<'EOF'`。发出后发现被吃了字——补一条说明，别装没看见。

## 三、中文变量名会给 shell 添乱

- **现象**：`目标="D:\…\工具\企微" && mkdir -p "$目标"` ——赋值那行报 `No such file or directory`（被当命令执行），
  后面 `"$目标/"` 变字面量，拷贝全落进一个叫 `$目标` 的怪目录。
- **根因**：bash 变量名只认 ASCII；中文名赋值不成立，`"$目标"` 不报错、只建怪文件夹。
- **对策**：shell 变量名用英文；**中文路径的批量文件操作改用 Python**（pathlib＋shutil，写 .py 再跑）；
  跑完立刻核对（`ls -d 目标目录`、`git status`）有没有多出怪东西。
- **注**：整理本包时又踩了一次——脚本里 `工作目录=…` 被当命令执行，报同一句错。

## 四、`/tmp` 不是一个地方

- **现象**：bash 里 `curl -o /tmp/b1.html` 成功；紧接 `node -e "fs.readFileSync('/tmp/b1.html')"` 报
  `ENOENT: D:\tmp\b1.html`。
- **根因**：bash 的 `/tmp` 映射到别处（本机实测＝`C:\Users\<用户>\AppData\Local\Temp`）；
  node/curl.exe 等 **Windows 程序**把 `/tmp` 当当前盘根下的 `\tmp`。
- **对策**：临时文件**写死绝对路径**（或 `%TEMP%` 的真实路径）；或同一条 shell 里用 sed/grep/awk 处理完，
  别跨程序交接；报 `ENOENT` 先看错误里解析出的**盘符路径**对不对。

## 五、长文本别用无引号 heredoc

- **现象**：用 `cat > 文件 <<EOF`（不带引号）写含反引号/反斜杠的正文，被 bash 做命令替换/变量展开：
  轻则内容被吃掉，重则 `bad substitution`、文件写坏、发出去是空白（有过板评被吃两段、API 报 422 的实例）。
- **对策**：长文本**用编辑工具直接落文件**，再整体喂给命令；heredoc 一律 `<<'EOF'`（带引号）；
  正文里别用反引号包路径；命令行用单引号包整个正文。

## 六、MSYS 会把 `/xxx` 参数当路径转换掉

- **现象**：`w32tm /query /source` → 报 `C:/Program Files/Git/query 未知参数`；`schtasks /tn …` 同理——
  开头的 `/query` 被 MSYS 当成了路径，替换成本地路径。
- **对策**：命令前缀 `MSYS_NO_PATHCONV=1`（例：`MSYS_NO_PATHCONV=1 w32tm /query /status`）；
  或者改用 `//query` 双斜杠写法（看工具支不支持）。

## 七、给 AI 的执行说明（速查）

1. 屏输出：`> /dev/null 2>&1`；见到 `nul` 文件 → 先备份再 `\\?\` 删（工具在 `模板\`）；
2. 带特殊字符的正文：单引号 / 写文件 / 带引号 heredoc；
3. shell 变量用英文；中文路径批量操作走 Python；
4. 临时文件用绝对路径，别跨程序传 `/tmp`；
5. 跑 `/xxx` 参数的工具加 `MSYS_NO_PATHCONV=1`；
6. 每步干完核对现场（ls / git status），被咬过的痕迹别放过。

## 九、实测记录（本机 Windows，2026-10-13）

- **nul 现场**：bash 里 `echo demo > nul` 真建出 `nul`（8 字节）；
  git-bash 的 `rm` 有时能删（MSYS 有特殊处理），**Python 的普通删法报 `WinError 5 拒绝访问`**；
  `\\?\` 前缀法成功（先备份到 `nul.内容备份.bin` 再删）。`模板\清保留名文件.py` 实跑通过。
- **/tmp 映射**：清理工具输出里看到，bash 的 `/tmp/…` 实际是 `C:\Users\<用户>\AppData\Local\Temp\…`——
  Windows 程序眼里却是 `D:\tmp`，本文第四条由此坐实。
- **路径转换**：`w32tm /query /source` 在 git-bash 里报 `C:/Program Files/Git/query 未知参数`；
  加 `MSYS_NO_PATHCONV=1` 后正常返回。
- **中文变量名**：整理本包时又踩一次——`工作目录=…` 被当命令执行（`No such file or directory`）。
