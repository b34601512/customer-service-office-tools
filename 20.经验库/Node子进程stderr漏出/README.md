# 经验包：Node 子进程的 stderr 会「漏」出来

> **一句话**：`execFileSync`/`execSync` 默认会把子进程的 stderr **直接打到父进程的 stderr**——
> 就算你 `try/catch` 了、也没写 `console.log`，失败信息照样漏：污染日志、让监听/守护脚本**假唤醒**。
> 修法是一行 `stdio` 收口。
> 用法：把本文件夹交给你的 AI，说「照这个包，把我脚本里调外部命令的地方收口」。

---

## 一、症状（真实案例）

- **监听/看门狗脚本假唤醒**：2026-10-11，一个「跟读监听」脚本的 `gh` 查询碰上网络瞬断，
  报错**漏进监听进程的 stderr**，监控把它当成「有新输出」→ 白叫醒一次（查了半天不是业务事件）；
- **日志分不清谁报的错**：定时任务里子命令的报错混进主程序日志；
- 明明 catch 了，终端上还是能看见子命令的报错——「我不是挡住了吗？」

## 二、根因

Node 的 `execFileSync`（以及 `execSync`，实测同样）默认把子进程 stderr **转发到父进程的 stderr**。
`try/catch` 只能把异常接住，**不能阻止已经发生的转发**。

```
子进程 stderr ──默认──▶ 父进程 stderr（漏！）         ← 日志污染 / 假唤醒
              └─同时──▶ 异常对象 e.stderr（也能拿到）
```

## 三、修法（一行）

```js
const 输出 = execFileSync("gh", ["api", q], {
  encoding: "utf8",
  timeout: 30000,
  stdio: ["ignore", "pipe", "pipe"],   // ★ 收口：子进程 stderr 只进异常对象，不外漏
});
```

一般规律：**监听 / 守护 / 循环脚本里调外部命令，一律收口**；失败信息只落日志或告警，
不许「顺手」漏到 stderr。

## 四、给 AI 的执行说明（照做）

1. **找**：搜代码里的 `execFileSync` / `execSync` / `spawnSync` 调用点；
2. **改**：加 `stdio: ["ignore", "pipe", "pipe"]`（spawn 系按同样思路配），补上 `try/catch` 与 `timeout`；
3. **验证**（怎么算修好了）：
   - 故意让子命令失败（跑一条必报错的命令），**父进程 stderr 应当为空**；
   - 失败信息能在返回值/日志里看到（`e.stderr`、`e.status`）；
   - 跑包里的 `复现\对比实验.cjs`，对照 stderr 上有没有「漏出行」。

## 五、包里有什么

| 文件 | 干嘛 |
|---|---|
| `复现\对比实验.cjs` | 「默认 vs 收口」对照实验——一跑就能看见漏与不漏 |

## 六、实测记录（本机 Node v24，2026-10-11）

`node 复现\对比实验.cjs 1>stdout.log 2>stderr.log`：

```
stderr.log 里只有 1 行：
[子进程] 我故意失败！          ← 来自「第 1 项：默认」，第 2 项（收口）没有
（两种情况下 catch 都能拿到：status=3，子进程 stderr="[子进程] 我故意失败！"）
```

`execSync` 默认同样会漏（实测：父进程 stderr 出现子进程的报错行）。

`node 模板\安全执行.cjs` 自测：

```
成功例： { 成功: true, 状态码: 0, 输出: '一切正常', 错误: '' }
失败例： { 成功: false, 状态码: 3, 输出: '', 错误: '出问题了' }
（本进程 stderr 行数：0 —— 收口成功）
```
