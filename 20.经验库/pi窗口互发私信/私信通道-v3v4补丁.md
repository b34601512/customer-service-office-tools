# 私信通道 · v3～v4.3 补丁 —— 从「忙时静默丢信」到「at-least-once」

> 本包自带的收信扩展是 **v2 基线版**（够用、简单）。但如果你把它用在**会话常常很忙**（流式输出、自动压缩、长回合）的环境里，会遇到一组「忙时丢信/重复投/队列饿死」的问题——本文件是那组问题的**演进史与修法**（生产环境实测，2026-10-12～13）。
>
> **一句话铁律**：投递类功能永远「**先确认再记账**」（at-least-once）——宁可重启后重投一次，**不可静默丢一次**。

---

## 病根：`sendUserMessage` 的失败会被吞掉

- pi 的 `sendUserMessage()` 是异步的；它在内部 `prompt()` 里可能**同步抛错**（典型：「Cannot submit a prompt while compaction is in progress」——压缩中不能提交），但扩展层包了 `.catch()` 把错误转成内部事件——**调用方拿到的返回值是 `undefined`，try/catch 也抓不到异步失败**。
- 所以：**不能依赖返回值判「投没投出去」**。这类「内部吞错」的依赖库 API，调用方在设计上就收不到失败信号。

---

## v3：游标只在「投出成功」后才推

**症状**：会话忙时到达的信，**游标推进了，但消息从没进过会话**——收件人不知情、发件人以为发了（真实漏网 10 封，都是最忙的几个窗）。

**修法**：

1. `取新信()` **只读不写**：从「已确认偏移」读到尾，算出候选新偏移**先不落盘**；
2. **空闲才投**：忙（含压缩中）就等 3 秒再看、最多 10 分钟；之后每 15 秒自动重试（欠着不丢）；
3. **投出成功 → 才写游标**；抛错 → 不推、稍后重试；
4. 半行（写一半）不投不推；末尾没换行但 JSON 能 parse 的完整行照收；同一批多封合并成一条投；**自己写的信跳过但推进游标**（不卡）；
5. 小日志记「投出/被拒」，正常静默。

**回归**：7 场景 24 断言全过（空闲直投＋推游标｜忙时不投不推、闲后补投｜忙时多封合并｜被拒不推、能投了补上｜半行不投、补全再投｜自己的信不推不卡｜离线期间的信开机补投）。

**教训**：**先记账（推游标）后投递 ⇒ 一次失败就永久丢，且不报错**——所有「防重＋游标」组合都要自查「被挡下时，这把『未完成』记在哪？」

## v4：忙不再等——`followUp` 排队 ＋ 投递码回执

**v3 的假设破了**：有的窗的节奏是**一个长回合贯穿全程**（拉起 → 一口气干完 → 收窗）——从拉起那一刻起 `isIdle` 可能**一次都不为真**，信一直欠着（不丢，但也不投）。

**修法（v4 两条）**：

1. **忙不等**：直接 `sendUserMessage(文, { deliverAs: "followUp" })`——pi 会把它排在当前回合收尾处投进会话（followUp 就是为「忙时排队」设计的）；
2. **靠会话回执确认**：每条投出的信抬头带一枚随机 6 位「投递码」（如 `（本地信箱通道 · xh3k9m）`）；投出后轮询本窗**最新会话文件**，**见到码才推游标**（≈90 秒内）；没见到＝欠着，5 分钟后再投。

**教训**：**「等到条件 X 才做」的设计，先问问 X 会不会永远不来**——「等闲」对长回合窗就是永不满足的条件。凡是等条件，要么给兜底（超时走别的路），要么换一个不依赖条件本身的机制（这里是 followUp＋回执）。

---

## v4.1：回执来晚了不能变成重复投 ＋ 回执只认「用户消息」

**问题 A（重复投）**：90 秒短确认对长回合窗太短——回执在回合收尾（几分钟后）才落进会话；而「欠着」只记在内存里，窗一关记忆没了 → 下次重开拿没动的游标**重投**（不丢，但重复）。

**修法 A（挂账落盘）**：

1. 短确认没等到 → 把「**码＋该推到哪**」写进 `.state\私信收.待确认.json`（挂账），然后每 30 秒后台看一眼会话——见到回执就推游标、清账；
2. **挂着期间不重复投**；
3. **重开先看账**：会话启动第一件事＝读挂账文件——码已经在会话里 → 直接推游标（不重投）；挂太久（默认 20 分钟）且窗已闲 → 判断真丢了，重投同一批（**换新码**）。

**问题 B（回执误认）**：旧版回执是「会话文件**整段原文**搜码」——排查时把码打印到输出/工具结果里，就会被当成「收到」，**游标白推、信没真投**（=静默丢）。

**修法 B**：逐行解析会话 JSONL，**只认 `type=message && message.role=user` 且内容含「本地信箱通道 · 码」的行**——码只会随扩展投递的用户消息进入会话，别的全不算。**宁可晚确认（最坏重投）也不误确认**。

**教训**：「**见到了 ≠ 它到了**」——任何基于文件/日志扫描的确认，必须限定**来源与角色**（谁写的、以什么身份出现）；「确认窗口」是**等待**不是**判定**，等不到≠没发生——结论要落盘、允许事后翻案。

## v4.2：跨会话挂账立即重投（别等「窗闲」）

**症状**：一条挂账堵住队列 43 分钟（一批在飞、不并行投是设计），但重投条件「20 分钟＋窗已闲」在按需时代**永远难满足**——窗「拉起就干活、干完就收」，没有闲点。

**真相**：那条「幽灵挂账」不是幽灵——它随**旧会话**消失了（旧进程没了，那条排队投递等不回来）。

**修法**：挂账记「**本会话 id**」：重查时对不上当前会话 ＝ 旧进程没了、那条投递**必然作废** → 立即重投（忙就排队）；**同会话**的挂账保持保守逻辑（可能还在排队里，不能急着重复投）。

**教训**：「等一下再重试」的条件里**别混入与本次机会无关的外部状态**（窗闲不闲）——重试触发应绑定**确定性事件**（进程/会话换了＝旧投递必然作废），而不是「碰巧空闲」。

---

## v4.3：`followUp` 被「收尾前收窗」截胡 → 改 `steer`

**症状**：按需窗轮次快（拉起→干活→自己收窗）；`followUp` 排在**回合收尾**，而窗在收尾前 3 秒就被关了 → 排队的信随队列消失（连投 5 次不达，信箱里的信一直「未读」→ 又触发拉窗，成环）。

**修法**：

1. 忙时投递由 `followUp` 改 **`steer`**（pi 的「回合中插话」：**步间插入、不打断工具批**）——窗在干活中间就看见信，来得及处理再收窗；
2. 每轮冲前**对齐游标文件**（手动收过信就采纳）；**确认推进只进不退**——防手动兜底后被旧偏移回投。

**明白这是 at-least-once 的正常代价**：最坏情况「重复投一次」；手动读信箱＋推游标是合法兜底（**会话还活着时手动推，扩展内存里的旧偏移可能让下一批多带一次旧信**——窗重开即自愈；**窗关了再推完全干净**）。

## 版本一览（给实现者）

| 版本 | 解决什么 | 关键机制 |
| --- | --- | --- |
| v2（本包基线） | 基本收发、关窗补投 | 游标＋fs.watch |
| v3 | 忙时静默丢信 | 游标后置（投出成功才推）＋等闲重试 |
| v4 | 长回合窗「等闲」永不满足 | followUp 排队＋6 位投递码回执确认 |
| v4.1 | 回执晚到→重复投；助手输出误当回执 | 挂账落盘＋重开先看账；回执只认 user 消息 |

## 五条通用教训（拿走就能用）

1. **投递类功能永远「先确认再记账」**（at-least-once）：宁可重投一次，不可静默丢一次。
2. **依赖库的错误处理要读实现**：内部吞错的 API，不能靠返回值判成功。
3. **等条件之前先问**：这个条件会不会**永远不来**？重试要绑定**确定性事件**，别绑外部状态。
4. **确认的匹配要限定来源与角色**：文件/日志里「出现了」不代表「它到了」。
5. **文件游标的三大经典坑**：半行、转义、编码——测试里各配一条。
