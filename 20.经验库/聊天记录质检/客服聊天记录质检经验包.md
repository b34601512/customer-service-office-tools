# 客服聊天记录质检经验包

> **一句话总结**：质检不是给客服打分，而是把「客户为什么走了」定位到「哪一句说错了」。要做到这一点，必须坚持**全量取数（防漏）、逐段通读（防假）、外部标记与内部判据分开记（防混）、判不出与没问题分开写（防骗）**。

在电商客服场景中，聊天记录数量庞大，靠人工随机抽查往往只能看到表面，甚至出现「报告全绿、客户却在持续流失」的假象。本经验包沉淀了一套可落地、可复核的售前聊天记录质检方法论，核心目标是：**保留完整上下文，用可回溯的原文证据判断客服是否真正解决了客户问题，并让收到反馈的人第二天就能直接改动作。**

---

## 一、判什么、不判什么

质检最怕「什么都想管，最后谁也不认账」。在动手看记录之前，先把边界划死：

### 1. 只判这三件事 + 一项外部事实
- **热情**：客户进线问什么，第一句是否正面接住。
- **主动跟单**：客户卡在某个节点时，是否主动给出了可执行、有帮助的「下一步」。
- **积极解决问题**：是否「问 A 答 A」，遇到答不上来或受限的问题时，能否说清原因并给出替代方案。
- **外部事实（平台标记）**：平台官方在会话中打出的客观标记（如「消极服务」「客户投诉」等），作为独立事实记录，不与内部判据混为一谈。

### 2. 明确不判的三件事
- **不判售后**：物流异常、配件补发、发票开具、商品故障及转接售后之后的服务不纳入售前质检。售前与售后是两条独立的责任线，混在一起容易把错算到错的人头上。
- **不判性格与情绪**：只判「这一段对话里的具体动作」，不给个人贴「态度差」「这人不行」的标签。性格改不了，但「这句话不该这么说、下次应该怎么答」可以立刻改。
- **不猜转接链路**：遇到会话发生过转接但上下文记录不全时，直接标为「待核实」，绝不靠猜测划分责任归属。

## 二、数据源与取数：如何保证「没漏」

### 1. 数据来源与采集方式
- **数据源**：从平台客服后台的会话记录页面导出原始聊天记录。
- **采集方式**：使用独立的浏览器实例（独立用户数据目录 + 独立调试端口）配合自动化脚本抓取，账号登录与图形/短信验证码由人工在现场完成，**不在任何脚本、配置文件或文档中存放账号密码与登录凭据**。

### 2. 取数策略：按天全量，拒绝「增量断点」
- **坚持按天全量抓取**：不采用「记录上次跑到哪、下次从断点继续」的增量模式。增量逻辑一旦某天中断或跨天偏移，极易静默漏掉中间几天的记录，事后补数的排查成本远高于直接全量重跑（实测 4 天约 430 段售前会话，全量处理约 2 小时即可完成）。
- **规避区间参数坑**：部分取数脚本在接收「起始日期、结束日期」两个参数时，可能只抓取头尾两天而忽略中间日期，且汇总日志依然打印「成功」。因此调用取数命令时，**日期参数一律逐天列全**（例如逐个列出每一天的日期）。

### 3. 三道对账机制（不以退出码为依据）
程序退出码为 `0` 只代表进程没有崩溃，绝不代表数据完整。每轮取数必须过三道对账：
1. **三数对账（抓到 / 筛出 / 保存）**：每天打印「原始抓到 N 段 → 按售前角色筛出 M 段 → 成功落盘 M 段」。**被筛掉的记录必须显式输出数量与原因**（最容易藏丢失的环节就是角色筛选——一旦识别不出新花名或临时账号，整段会话就会静默消失）。
2. **落盘文件对账**：脚本跑完后，按文件名中的日期分组统计落盘文件数，与平台后台当天列表显示的会话总数逐一核对。
3. **平台标记对账**：在导出的全部聊天底稿中，全文检索平台标记原文（例如「当前会话您存在消极服务行为」），先拉出一条客观的「平台已判定清单」，再与人工逐段质检出的问题清单交叉比对。

## 三、判断标准（带依据与正反例）

### 1. 三个核心维度的判定证据

| 质检维度 | 合格标准（看什么证据） | 反面示例（不合格） | 正面示例（合格） |
| :--- | :--- | :--- | :--- |
| **热情** | 第一句即正面接住客户诉求 | 客户发来商品链接询问细节，客服只回「在的」「您好，请问有什么可以帮您」 | 客户发来商品链接，客服首句即围绕该型号的关键参数或适用场景展开回应 |
| **主动跟单** | 在客户卡点处给出「下一步」 | 客户问「明天急用今天能发吗」，客服只答「不能哦」 | 「可以帮您备注加急发货，但无法指定快递；如果特别急用，建议先看看同城是否有现货」 |
| **解决问题** | 问 A 答 A；受限时说明原因并给可执行动作 | 对专业或合规受限的问题直接敷衍「不知道」「不清楚」 | 「这个指标我们不能随口替您换算，建议您按机器额定流量使用，具体用氧量以医嘱为准」 |

### 2. 什么算「消极服务」：平台口径 vs 内部口径

平台判定与内部质检关注点不同，**必须分开记录、互相印证**：
- **平台口径（看客户是否被晾着）**：当客户持续追问，而客服长时间未回复、或连续发送无实质推进的固定模板时，平台系统会在会话正文中写入标记。这是客观发生的外部事实，不能争辩，必须如实记录。
- **内部口径（看哪一步错了、能不能改）**：重点抓三类具体动作失误：
  1. **同段前后矛盾**：同一会话内给出两个相反口径（客户照前一句买会错、照后一句买才对）。
  2. **模板复读**：客户问题已经推进或变化，客服仍在连续复读同一句模板话术。
  3. **忽略已给信息**：客户已在前文明确提供了条件（如使用场景、具体需求），客服仍反复索要同一个信息。
- **两者的关系与实测规律**：平台标记告诉你「哪里疼」，内部判据告诉你「哪里在出血」。只看平台标记等于等处罚落地才反应；只看内部判据则容易忽视平台累计扣分风险。在某轮 4 天 430 段售前会话的实测中，平台共标记 8 起「消极服务」，其中 6 起均可直接归因于「同段给出相反口径」或「同句模板反复追问」。**这说明：被平台判消极服务，往往不是因为「回得慢/回得少」，而是因为「回答自相矛盾或原地绕圈」。**

### 3. 「判不出」与「没问题」必须严格分开
这是质检报告最容易失真、最容易「造假」的地方：
- **判不出（写「待核实」）**：证据链不完整——例如转接后的后半段聊天未取到、系统提示消息未落盘、客户仅发送了表情或无意义字符。必须写明「待核实」及具体缺失的证据项。
- **没问题（写「合格」）**：已逐句通读完整上下文，确认没有可指正的具体动作失误。
- **混用的后果**：把「没取全/没看清」直接记成「没问题」，会导致报表一片绿灯，但客户体验和转化率仍在悄悄下滑。

## 四、踩过的坑与避坑规范

1. **通读 vs 抽样的边界**
   - 抽样只能支撑「团队整体表现尚可」的宏观结论，**无法支撑「某位客服在某段会话做错了」的个人定责**。只要报告要落到具体人和具体会话，就必须逐段通读。若历史天数确实补不回来，可退一步仅扫描平台标记，并在报告开头**显式声明「某几天仅查标记、未通读」**——把覆盖成本写在明处，远比假装读过更可信。
2. **如何区分「标准话术」与「模板复读」**
   - 不看字数长短，只看**有没有随客户问题而变化**。同一句话在几十个不同会话里各出现一次，属于正常的「标准话术」；同一句话在**同一个会话**内出现 2 次以上、且客户的问题已经往前推进，就属于「复读」，应判为问题。核心判据只有一句：**这句话有没有回应「客户刚说的那句」？**
3. **同段前后矛盾的记录方式**
   - 严禁只写「口径混乱」四个字（无法与当事人对质）。必须固定记录四要素：**时间点 + 客服原话 A + 客服原话 B + 客户当时的提问**。
4. **高频参数先做「口径卡」，先区分集体问题还是个人问题**
   - 如果某个高频参数（例如「要不要加水」「选几升机型」「能否 24 小时连续开机」）在多轮会话中出现多种不同说法，应先把所有说法汇总成一张「参数口径卡」并推动业务统一标准。**跨人不一致，先归因于「团队口径未统一」，不扣到单个客服头上；只有同一个人在同一段会话里「自己打自己」，才算个人动作问题。**
5. **时效问题单独归类为「值班空档」**
   - 凌晨或非工作时间进线的留言，到次日开班才回复，若连续多天呈现同一时段特征，应归类为「值班/排班空档」，而不是给某位客服贴「态度差」标签。判断依据是「连续性 + 时段」，而非单条延迟。
6. **严格的脱敏规范**
   - 对外或跨组流转的报告与案例，统一使用 `客户1 / 客户2`、`客服A / 客服B` 代称；手机号、收货地址、订单号一律删除或打码；引用对话原文时只截取能说明问题的两三句，不贴整段聊天记录。
7. **工具与执行细节坑**
   - 自动化取数时，浏览器窗口切勿最小化（系统的后台节流机制可能导致页面抓取静默中断，日志却显示跑完）。
   - 临时文件切勿使用固定文件名（多任务或多人共用环境时容易互相覆盖串档）。
   - 所有对外或向下发出的通知、报告，发送后必须回读确认一次。

## 五、标准样例流程（可直接照跑）

### 第 1 步：逐天全量取数
```bash
# 1. 启动独立浏览器实例（人工完成登录与验证码）
browser:start

# 2. 先核对当天售前会话总数
fetch:list --start 2026-10-28 --role 售前

# 3. 逐天列全日期批量落盘，不使用起止区间简写
batch-save 2026-10-28 2026-10-29 2026-10-30 2026-10-31
```

### 第 2 步：三道对账（不通过不往下走）
- 核对每天的 `抓到 / 筛出 / 保存 / 失败` 四个数字；
- 按文件名日期分组计数，与平台列表总数对齐；
- 将「被筛掉的会话数量及原因」写入底稿备查。

### 第 3 步：导出底稿并扫描平台标记
```bash
# 导出带时间戳的纯文本底稿（一条消息一行）
dump-chats 2026-10-28 2026-10-29 2026-10-30 2026-10-31 > raw.txt

# 检索平台官方标记原文，生成外部事实清单
grep "平台标记原文" raw.txt
```

### 第 4 步：逐段通读与三行判定
每读完一段会话，固定写完三行再进入下一段：
- **客户要什么**：一句话概括核心诉求；
- **客服做了什么**：只写客观动作，不复制大段模板原文；
- **差在哪**：指出具体缺失或矛盾点（无问题则写「合格」，证据不全写「待核实：缺 XX」）。

### 第 5 步：按固定五节结构出报告
1. **覆盖范围**：本次通读了几天、多少段，**哪些没读、为什么没读**（缺此节则报告不可信）。
2. **外部事实**：平台标记共几起，列出时间点、对象代称及被标前的一串动作。
3. **内部判据**：口径矛盾、模板复读、漏答、迟答各几例，每类精选 1~2 个典型原文片段。
4. **正面亮点**：答得好的原文片段（必须保留，否则报告只剩挑刺，团队很难接受第二轮改进）。
5. **改进建议**：不超过 3 条，且每条都必须落到具体动作（例如：补齐某参数口径卡、禁止同段给出相反结论、明确凌晨留言首响机制）。

### 第 6 步：点对点反馈（改进机制）
- 坚持**一条一事、只发本人**；
- 反馈内容只包含：**2~3 句对话原文 + 哪里不对 + 下次该怎么说**；
- **不搞公开排名、不发大群点名、不抄送无关第三方**，保护一线客服接受改进的意愿。

### 第 7 步：收尾与断点交接
关闭浏览器实例，将「今天读到哪一天、哪一段未读完、明天从哪接续」写入本地交接断点记录，确保下一轮质检或接手人可以无缝续跑。

## 六、验收判据（如何判断这份质检合格）

一份合格的客服质检报告，必须同时满足以下三条硬标准：

1. **证据可回溯（指得出原文）**：报告中每一处扣分或问题定性，都能精确指回原始聊天记录中的**哪一段、哪一句话、哪一秒**；绝不允许出现「感觉服务态度一般」「整体回复较慢」等无原文支撑的模糊评价。
2. **覆盖诚实（不隐瞒盲区）**：报告明确交代了全量基数、实际通读数、筛选剔除数以及「待核实」项，不存在把「没取到/没读完」包装成「没问题」的情况。
3. **动作可执行（第二天能改）**：收到反馈的客服或业务负责人，看完后不需要再追问「那我到底怎么改」，第二天上岗就能直接按建议调整话术或补齐口径卡。
