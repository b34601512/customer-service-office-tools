# 结论要带判据：现象 ≠ 判据；「采信某人」不算依据

> **作者：情报专员·苗若兰**（2026-10-18 原样收入 20.经验库，内容未改一字；原文在 `D:/硅基公司/员工/情报专员·苗若兰/经验/`）

- **日期**：2026-10-18（与推广专员·钟灵来回推了三轮，最后钉成的口径）
- **由来**：我读宽了一次（把「DBSC 文件存在」当成「功能启用」），钟灵一句「用一个能查的事实去支撑一个查不到的结论」点出来；我补上「现象 → 判据 → 结论」这一层，她把六次错误按这个框架重排，于是这条规矩成型。

## 一、三层结构（缺中间那层，判断就会飘）

```
现象                →  判据（写下来，可执行）        →  结论
401 返回            →  配合 sitemap/官方文档双证      →  路由在（且不收费）
Device Bound Sessions 文件在 → select count(*) from dbsc_session_tbl > 0 → 真启用了设备绑定
公告点名 A/B/C      →  实测那个具体产品                →  谁能用、谁不能用
profile 里没登录票  →  （只能支撑前半句）              →  「平台记成新设备」是推断，要标注
```

**要点**：原则是抽象的（"要小心""别读宽"），**不可执行**；判据是具体的，可复核。
只记原则、不记判据，换个新场景照样错——**我就是在自己写过这条原则之后又错了一次**。

## 二、「采信某人」不算依据

汇报/材料里写「据技术说」「据同事核查」，等于把责任转移给一个不可复核的句子。
改成：**采信谁的什么命令、什么输出**。

- ✗ 「技术确认服务器在深圳」
- ✓ 「`grep oss-cn- /etc/softtalk/*.env` → `oss-cn-shenzhen`」

这样将来要复现、要质疑，都有抓手。

## 三、判据要能自证（给别人看也要能复核）

给同事的每条结论都附「我在哪查的、看到什么值」，对方就能自己验一遍，而不是"信你"。
对方能不能复核，决定了这条情报是**资产**还是**传闻**。

## 四、关于"错得多"

钟灵 2026-10-18 的话，值得记：
> 「错误的密度高，说明我今天在做的活密度也高……真正可怕的是判断很多但从不犯错——那通常意味着每次都在舒适区里，没碰到边界。」

前提是**每次错误都要留下判据**，否则错得再多也不长进。

> 配套：`接口存不存在用活体探测-401不等于404-公告名单别读宽.md`（同族读宽案例）、`验证码别硬破-减少触发比识图划算.md`（DBSC 那次的现场）

## 五、复盘的目标不是记录痛苦，是产出判据（钟灵 2026-10-18）

她的原话，我认同并采用：
> 「其余那些『我今天错了六次』这种话对别人没用。别人不需要知道我错了几次，需要知道下次怎么不出错。」

**自检法**：写完一段复盘，问一句「下一个人照这句能不能少错一次？」
- 能 → 这是判据，留下
- 不能 → 这是情绪，删掉或压成一行

**对比（同一次错误，两种写法）**：
- ✗ 「我今天又读宽了一次，很懊恼，这是我第二次犯同类错。」——只有情绪，别人拿不走
- ✓ 「文件在 ≠ 功能在；判据是表里记录数 > 0。」——任何人下次都能执行

**为什么这条重要**：情绪化的复盘写多了，会把真正的判据稀释掉——以后翻回来看，全是「我又错了」，找不到「我该怎么判」。

## 六、0 条记录怎么说话（预先写好的判据，2026-10-18）

「跑出来是 0」和「对方没启用」之间隔着一整个判据。三种结果三种说法（口径形成于 2026-10-18）：

| 跑出来 | 能说 | 不能说 |
| --- | --- | --- |
| 记录数 **> 0** | 「确认在启用，判据成立」 | — |
| 记录数 **= 0** | 「**本次未观测到**，无法判断」 | ❌「没启用」（0 条可能＝没启用，也可能＝还没触发） |
| 跑不出来/报错 | 「本次未取得数据」 | ❌ 任何推断 |

**「分不出来就说分不出来」**——这句话本身就是一条判据。它比"要谨慎"可执行得多。

## 七、预先写判据 ＞ 错完再补

同一类错误，两种时机：
- **事后补**：错完 → 复盘 → 写下判据（前 6 次都是这种）
- **事前挡**：还没做，先把判据写下来 → 做的时候照判据说话（第 7 次是这种）

**事前挡的效率高得多**：错完再补要付一次错的代价，事前挡零代价。
做法也很简单——**在动手之前，先把"我要看什么值、每种值能说什么/不能说什么"写下来**，再去看。

## 八、出处怎么标：四档＋「无判据」不是留空（钟灵 2026-10-18 落地版）

每行判据都要能指回「在哪看到的」，但要分档写，别糊成一句「查过了」（本表 2026-10-18 定）：

| 判据来源 | 写法 |
| --- | --- |
| 源码类 | **文件名 + 行号 + 函数名** |
| 命令类 | **完整命令 + 输出** |
| 他人提供 | **谁 + 什么时候 + 做了什么查证** |
| 没有判据的推断 | **明确写「无判据」**（不要留空） |

**「留空」和「写无判据」不一样**：留空看起来像忘了填；写「无判据」是明确告诉后来人——这一格认真想过了，确实没有。

## 九、没有出处的判据，会在传递中悄悄扩大适用范围（最危险的一种）

钟灵举的实例：他引用程灵素说的「本地范围禁网」，如果只留下这句话，
半年后既不知道它出自 `controller_runtime.py:270-280` 的注释，也不知道它的**边界**
（只对话术文本成立，附件走 `is_cloud_phrase_scope`）。

> **忘掉会重新查，扩大了却不会**——所以「没有出处」比「忘掉」更危险。

情报岗同理：一条结论传三个人之后，往往只剩「XX 说可以」，边界、条件、日期全丢了。

## 十、判据表要分两张：复盘表 vs 速查表

- **复盘表**（我错在哪）：给想校准的人看，一行一次错，写「缺的判据是什么」。
- **速查表**（以后怎么判）：给想直接用的人看，一行一个判据，写「看到什么值 → 说什么 / 不能说什么」。

内容会重叠，但**读者不同**——混成一张表，两种人都用得别扭。

## 十一、出处也会过期：出处要带「日期」

第八节的四档只解决了「在哪看到的」，还差一层：**什么时候看到的**。

- 链接还在 ≠ 内容没变（平台规则会改版，我今天查的三家平台规则就标了「页面最后修改日」）
- 命令输出有时效（`select count(*)` 昨天是 0，今天可能是 3）
- 「XX 说可以」也有时效（他能说那句话时的版本，跟现在的版本未必一样）

**所以出处的最短形态是：`在哪 + 什么时候 + 看到什么`**。
我交付情报时每条都写「抓取日期」，就是这个道理——**没有日期的出处，等于没有出处，只是看起来有。**

三档时效（本表 2026-10-18 定）：
| 出处类型 | 多久会失效 | 建议 |
| --- | --- | --- |
| 官方规则/文档链接 | 数周到数月 | 必标抓取日期 + 页面自带修改日期 |
| 命令输出（数据/状态） | 分钟到天 | 标执行时间，重要结论重复跑一次 |
| 他人提供 | 视版本而异 | 标「谁、何时、在哪个版本上查的」 |

## 十二、「有出处」也只是现象：日期那一格才是判据（2026-10-18 钟灵自查）

她按第十一节自查自己那张 14 行的表，结果：**只有 3 行有日期，11 行没有**。
而且最讽刺的是——**引源码行号的那几行全都没日期**（`phrase_xlsx_codec.py:79-105` 是她当天几小时前核的，但表里看起来像一条永远成立的规矩）。

**她给自己的解释，比我那节写得更准**：
> 「读的时候脑子里默认"有出处 = 完整了"。看到有出处列 → 认为出处完整 → 实际缺了最关键的时间维度。」

**这是「用现象当判据」的第 N 次**：
- 现象：有「出处」这一列
- 误判：出处完整了
- 缺的判据：**那一格里有没有日期**

**可执行的自查法（比"要写日期"具体）**：
```bash
# 数一数：有出处列的行 / 有日期的行
grep -c '^|' 表.md          # 总行数
grep -cE '20[0-9]{2}-[0-9]{2}-[0-9]{2}' 表.md   # 带日期的行
```
两个数不等，就说明有行缺日期。**别靠读，靠数。**

## 十三、命令类出处要附「需重测」的边界

她补日期时给命令类出处特意加了一句「页面若有增删需重测」——
因为 `curl` 出来 6 个页面，将来可能变成 5 个或 7 个；不写这句，后来人会以为「官网永远 6 页」。

**规则**：出处的日期后面，跟一句**这条证据什么条件下会失效**。
- 源码行号 → 「该文件改版后需重核」
- 命令输出 → 「页面增删/数据变动需重测」
- 平台规则 → 「规则修订后需重查（季度复核环已挂）」

## 十四、分清两类表：证据表逐行带日期，规则表整表带日期（2026-10-18 自查后修正）

我照第十二节去数自己的表，发现三张「规则表」全都没日期——写了「没有日期的出处等于没有出处」，自己却没做到。
但补的过程中发现要求得分开，否则会矫枉过正：

| 表类 | 内容 | 日期要求 | 理由 |
| --- | --- | --- | --- |
| **证据表** | 引用的源码行号、命令输出、他人查证结果 | **逐行带日期** | 每行时效不同（行号随文件改、输出随数据变） |
| **规则表** | 自己定的口径、判据分档、用语规范 | **整表带一个日期** | 整表同一天定、同一天改 |

**规则表也逐行标日期的坏处**：变成一堆重复的 `2026-10-18`，把真正需要看日期的那几行**稀释掉**。

## 十五、markdown 表格里的「真换行」会把行截断（发现者：钟灵；触发条件：我提出「出处必须带日期」）

- 现象：表里写了 `TextBlock("\n")`，但那个 `\n` 是**真实换行符**（不是字面量），把表格行截成两行。
- 后果：**渲染出来表格断掉**，而**编辑器里看着像正常折行**，肉眼看不出来。
- 发现方式：写脚本按行扫（`grep -c '^|'` 数行），不是靠读。
- 判据：**别信肉眼看到的排版，去扫结构**（跟「别信提示语、要看实际内容」同族）。

**检测方法（必须能执行，否则等于没写）**：
```bash
# 以 | 开头但结尾不是 | 的行 = 单元格里混进了真换行
grep -n '^|' 表.md | grep -v '|$'
```
**根因**：markdown 单元格里不能有真实换行；要写字面量就用代码块或写成「反斜杠+n」。

**署名口径（按“作者+时间+做了什么”）**：
> 发现者：钟灵（扫表时偶得）；触发条件：苗若兰提出「出处必须带日期」

## 十六、标注的价值在于区分度，不在密度（钟灵 2026-10-18）

> 「如果满屏都是 2026-10-18，读者就分不清哪一行是今天核的、可能会变，哪一行是这条规矩就这么定的。」

**同族道理：告警误报** —— 信息量被噪声淹没，读者就开始忽略全部告警。
所以：
- 需要**区分**的地方才标（证据表逐行），
- 不需要区分的地方标一处就够（规则表整表），
- **宁少不多，标出来的每一处都要有信息量。**
