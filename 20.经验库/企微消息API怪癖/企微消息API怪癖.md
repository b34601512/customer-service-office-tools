# 经验包：企微（智能机器人）消息 API 怪癖合集

> **一句话**：跟企微机器人对接，**按直觉写处处吃坑**——但坑都是实测出来的，照本包躲开。
> 覆盖 6 个亲测怪癖：群里只有真 @ 才推、@所有人/webhook 都喊不动机器人、多图只存第一张、图片下载先重试再手动取、发信人名字常为空、机器人发的 @ 是普通文字。
> 附一个可复跑的「手动取图」小工具。

**适用**：用「智能机器人＋长连接」做消息收发的自建 AI 助手机系（搭建见同库《企微 AI 员工体系-从零搭建》）。

## 怪癖 1：群里只有「真 @」才推给机器人

**现象**：老板在群里发长消息，@ 的全是手打的 `@技术…` 文字——机器人**收不到**（服务端日志零回调）；随后从弹出成员列表**点选**的 @ 测试——收到了（`chattype:"group"`）。

**结论**：

- 企微里手打 `@名字` 只是普通文字；**必须输入 @ 后从弹出列表点选**（显示成蓝色链接）才是「真 @」。
- 真 @ 才会把消息推给对应的机器人——**平台自带的点名过滤**：群里 18 个人，@ 谁谁收到，连脚本都不用，天然省 token。
- 机器人**看不到群里的普通聊天**（不 @ 不推）。

**用法建议**：定向喊人＝群里真 @；全公司通告＝公告板（板＋点名制），群只当急事通道。

## 怪癖 2：@所有人、webhook、机器人互 @——都喊不动

实测三连（全部零回调）：

| 测试 | 结果 |
| --- | --- |
| 人在群里 @所有人 | ❌ 不推给机器人（只推「直接 @机器人自己」） |
| 机器人往群里发 `@某某 测试` | ❌ 只是普通文字；闭环实测：机器人 @ 自己都没推回来 |
| 群 webhook 直发文本 | ✅ errcode 0（群里可见） |
| webhook `mentioned_list:["@all"]` | ❌ 机器人们零回调 |
| webhook 点名机器人（`mentioned_list:["aibbh-…"]`） | ❌ 请求被接受但**不推给机器人** |

**为什么**（一句话）：**「@人」和「@机器人」是两条通道**。

- 人是通讯录成员（有账号）→ webhook 的点名名单只认通讯录账号；
- 机器人在系统里是「应用」→ 不在通讯录名单。你在手机里能 @ 到它，是企微客户端另有一条**应用消息通道**（长连接收到的回调就是这条通道）；webhook 没有这条通道的钥匙。

**结论**：喊机器人的正路只有两条——①人在客户端**真 @**（或私聊）；②机器人之间走公告板。webhook 的价值在「往群里发东西给人看」（可做紧急告警喇叭：守护掉线吼一声到群里），但它 @ 不动机器人。

## 怪癖 3：一条多图消息，只存了第一张

**现象**：一条图文消息带 3 张图，收件箱只落 1 份文件；守护日志里 `media` 只有一个 url。

**根因**：提取媒体的代码写成了「遇到第一份就 `return`」——后面的图片**连记录都没进**。

**修法**：

1. 提取**列表**（走完整个 `msg_item`，图片/文件/视频/语音都收）；旧的单份取法改成「列表的第一份」保持兼容；
2. 落盘遍历列表逐份下载，文件名加 `-1/-2/-3` 后缀防冲突；记录里存「媒体路径列表」；
3. 查看端：几份媒体就列几个文件名。
4. 改完**要重启常驻守护**（Node 启动时加载代码，不重启不生效）。

**抢救已丢的图**（链接 5 分钟过期，要快）：

1. 原始报文在守护日志里（`mixed.msg_item[…]` 带 `url`＋`aeskey`）；
2. 按顺序配对抓出 `url+aeskey` 下载（拿到的还是密文）；
3. 解密：**AES-256-CBC，key＝base64 解 aeskey（32 字节），IV＝key 前 16 字节**，再去掉 PKCS#7 填充 → 明文 JPEG（验头 `ffd8`）；
4. 校验：解出的 sha 与已落盘的那张一致＝配对没错。

**教训**：

- **「落盘的记录」不等于「真实收到的」**——先翻原始报文，差异往往在那儿一眼看出；
- 一条消息带多份媒体是常态（客户会连发现场照片）——凡是「提取单个」的写法，都问自己「**多份怎么办**」；
- 客户证据类媒体**链接过期就没了**，落盘要趁早；发现丢了先抢救、再修代码。

## 怪癖 4：图片下载失败——先重试，再手动取

**症状**：守护日志出现 `媒体下载失败（第 1/1 份）：stream has been aborted`；`media/` 里没有新图。

**要点**：

- 首次失败**多为瞬时**——先自动重试；重试还不行再手动取；
- 媒体 **url 带签名，`q-sign-time` 只有 5 分钟有效**——收到就取，别拖；
- 手动取＝拿记录里的 `media.url`＋`media.aeskey` 下载＋解密（算法同怪癖 3）。

配套工具：同目录 `工具\取企微图片.cjs`（支持 http(s) 下载与本地文件；只读、不打印密钥；带离线冒烟测试）：

```bash
node 取企微图片.cjs --url "https://…" --aeskey "…" --out 收件箱/media/msgid.png
```

离线冒烟测试：`node 测试\冒烟测试.mjs`（2026-10-14 本机 **9/9 过**：两种 key 写法、sha 一致、输出不泄露 key、三种错误退出码）。

## 怪癖 5：`fromName` 常为空——用 userid 对人

**现象**：收件箱记录里的 `fromName` 经常是**空的**，只剩 `fromUserId`（一串平台内编号）——回复/汇报前先把人对上，别认错人。

**做法**：

1. 建一张「userid ↔ 名字」对照表（谁第一次出现就补一行；表不含密钥级信息，但也不宜进公开仓库——放本地/内网）；
2. 取名单的现成通道：机器人会话列表命令（`npx wecom-cli message aibot sessions list` 之类，拿 `chat_name`）；
3. 对不上时翻收件箱原文（每条都带 `fromUserId`），按「读最新几条 → userid → 查表 → 处理/回复」的流程走。

**教训**：消息处理里**别靠 `fromName` 判人**（它可能是空）；一律用 `fromUserId` 查表，未知 id 当「陌生人」处理（查清楚再回）。

## 怪癖 6：机器人发的 @ 不会让对方收到

机器人发的消息里 `@某某` 只是普通文字：**@不了别人、@所有人也喊不动**（闭环实测：机器人 @ 自己，零回调）。

**定位**：群＝**人对机器人的定向通道**（人 @ 谁、谁收到）；**机器人之间互相叫还是走公告板**（板＋点名制，设定「谁被点名谁处理」的纪律）。

## 相关

- 长连接 vs URL 回调：本机窗用**长连接**（主动拨出、免公网）；要挪到公网服务器再评估 URL 回调（需要公网 HTTPS 地址）——两者选型见《企微 AI 员工体系-从零搭建》部署一节。
- 密钥纪律：Bot ID/Secret、webhook 钥匙、Token/AESKey 都是**密钥级**——不进 git、不发群/板、截图打码。
