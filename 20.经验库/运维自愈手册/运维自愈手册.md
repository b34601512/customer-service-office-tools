# 经验包：运维自愈手册 —— AI 员工体系的「保命」实践

> **一句话**：体系**搭起来**只是开始，**长期跑得住**靠的是——坏了有东西知道、坏了有东西修，而不是等人踩。
> 本包是《企微 AI 员工体系-从零搭建》（同库）的续篇·运维篇：**10 个真实故障 → 6 条自愈原则 → 可照抄的巡检表与验收清单**，附一个已实测的通用「自巡查」小工具。
>
> **用法**：①先背「六条原则」；②出事按案例对号入座（症状→根因→修法）；③定期照《模板\巡检表.md》体检；④搭完体系照「验收清单」自己出三关。

## 〇、开篇：最危险的故障是「静默失效」

系统出故障时，最坏的不是「坏了」，而是「**坏了没人知道**」：

- 叫醒器断了 → 消息不叫人、闲置不收窗，整个「按需开窗」体系瘫痪，但表面上一切正常；
- 开机自检被顶掉 → 窗口开着、人也在线，但听不见消息；
- 自动收窗把后台任务一起杀了 → 干到一半的活没了，没人知道。

真实教训：**同一天内两起**，全靠老板/同事踩到才发现（老板发现员工不回消息；同事急报窗口不理人）。本手册的目标：把「等人踩」变成「**机器自己发现、自己兜底、自己吼出来**」。

### 先记一个关键认知：链路是「三件套」，缺一不可

一间「能干活、能自己醒」的 AI 员工窗 ＝ **收件守护（在）＋ 监听跟读（在）＋ 唤醒环（在）**。

只查「进程在不在」会得出**假绿**——真实案例：有一次第二扇窗恢复会话时把老窗的唤醒环**悄悄退役**，进程还活着、监听还亮着，收件箱再响也没人醒，晚了 13 分钟才被补课。所以：

> **「进程在」≠「能干活的窗」。**

## 一、六条自愈原则（先背原则，再看案例）

1. **静默失效要有哨兵**：监控必须**独立于被监控者**（叫醒器自己断了，不能靠叫醒器报告）。哨兵要「正常全静默、坏了主动吼」——否则天天刷屏没人看，等于没有。
2. **关键常驻进程配「定期巡查＋不在就拉起」**：手动起的进程活不过重启；查岗最快的方法＝**看它自己的日志时间戳是否还在长**。
3. **状态推进（游标/基线/标记）一律后置**：**先做成、再记位**。反过来（先记位、再动作）＝一次失败就永久丢，而且不报错、最难查。
4. **身份判定要「刚性」**：别靠工作目录（CWD 是调用环境的，不是目标的）；别拿子串当身份；别用「空值＋exists」找路径；认一个「家」要认**特征文件**。
5. **防撞车/防刷要限定范围**：凡「查有没有别的进程在跑」式的互判，必须限定「**本窗/本项目**」；否则开机补跑、并发场景会群体自锁。
6. **出错要大声**：干不了就报错、非零退出；静默的「假装成功」比报错危险十倍。**别用 `| Out-Null` 吞报错**——真实案例里这条让一个出厂就有的 bug 潜伏了一周。

## 二、十个真实案例

> 格式：症状 → 根因 → 修法 → 验证 → 记住什么。案例里的人名/路径都做了泛化，做法原样可抄。

### 案例 1｜叫醒器断链：机器重启后，「按需体系」整体失聪

- **症状**：早上 06:48 机器重启（前一晚关机）。06:57 例行检查发现叫醒器没在跑——它的日志停在昨晚 22:38。整个「新消息→自动拉窗」链条断了，直到手动拉起才恢复。
- **根因**：叫醒器上线时是**手动常驻**（在会话里起了一个隐藏进程）。机器一关，进程消失；重启后没有任何机制把它拉回来。事前没发现，是因为「当时它在跑」＋「别的组件都自启了」容易让人以为它也在自启名单里。
- **修法**（已落地）：
  1. 叫醒器加**单实例守卫**：启动时先查进程表，已有实例就直接退出（防空跑/打架）。
  2. 装**计划任务「每 5 分钟巡查」**：不在就隐藏拉起；设置 `StartWhenAvailable`，重启后自动补跑。
  3. 隐藏壳走成熟套路：`wscript（run-hidden.vbs）→ wake.ps1（UTF-8 BOM，认中文路径）→ Start-Process node -WindowStyle Hidden`（进程独立，壳退出不影响它）。壳里也查一遍「已有实例」，与程序里的守卫**双保险**。
- **验证**：杀掉实例 → 下次巡查自动拉起；重复巡查静默跳过。
- **记住什么**：**关键常驻进程必须配「定期巡查＋不在就拉起」**，别指望手动起的进程活过重启。

### 案例 2｜链体检：给「静默失效」装一个哨兵

- **症状**：一天里两起静默失效（案例 1 的断链、案例 8 的丢自检），**都是人踩才发现**——监控存在与否，无人检查。
- **对策（链体检）**：一个独立计划任务，每 10 分钟跑一轮：
  - **查什么**：每个开着的公司窗：①收件守护在不在；②监听跟读在不在（③唤醒环是不是还活着——见案例 9）；④叫醒器在不在（它断了＝按需叫醒全停）。
  - **坏了怎么办**：给值班人/技术窗发私信（叫醒器会把人拉起来修）；同一故障 **30 分钟只吼一次**；**正常全静默**。
  - **成本**：纯脚本查进程表/进程树，**0 token**；只有坏了才唤醒一次窗。
- **关键设计（踩坑所得）**：
  - **监控必须独立于被监控者**：链体检不挂在叫醒器里，而是独立任务——叫醒器自己断了它还能报告。
  - **进程归属别按命令行硬认**：监听命令只有相对路径（认不出是哪家的），归属要**顺着进程树/父链**找（从窗的 pi 进程往下找后代，兜底向上找带自检单的祖先）。
  - **刚开机的窗给 2 分钟宽限**：链路是开机后逐条挂的，太早判会误报。
  - **发电前限流**：30 分钟/故障，防刷屏。
  - **发信走统一通道**：用套件的发信工具，别自己刻字段。
- **验证**：`--干看` 全健康 0 问题；`--演练` 造假故障 → 告警端到端到达。
- **记住什么**：哨兵的价值＝**坏了主动吼**；「正常静默」是它不讨人嫌的关键。

### 案例 3｜防刷挡下拉窗 → 游标被吞 → 消息永不再试

- **症状**：老板报「给某员工发消息没回复」。一查：消息静静躺在她收件箱里，**窗没被拉起来**。
- **时间线（根因）**：
  - 20:42:50 叫醒器拉过她的窗 → 20:44:39 她答完自己收窗；
  - 20:45:29 老板新消息落进收件箱；
  - 20:45:48 叫醒器看到新消息，却按「3 分钟内刚拉过，先不重复」跳过——**而消息游标（文件字节）在更早一行就被推到了队尾**；此后每一轮都「没有新动静」，这条消息**永远不再被处理**。
  - 同款第三处：排期环投信后**先推字节基线再拉窗**——拉窗被挡，投的信同样被永久吞掉。
- **修法**：拉窗动作返回「**有没有着落**」——窗活着会自己读 / 拉窗成功＝true；防刷挡下 / 没有开窗器 / 开窗器报错＝false。所有投递方（私信、收件箱、排期环）**只在 true 时推进游标**；false 就留着，下一轮再试。被挡下的日志限频 10 分钟一条，不刷屏。
- **验证**（真机三关）：①关窗投信 → 20 秒内拉起成功、游标推进；②3 分钟内再投 → 跳过、**游标不动**；③防刷期过 → 自动补拉、游标推进。
- **记住什么**：**「推进游标/记标记」永远放在动作成功之后**。自查同类：任何「防重/防刷＋游标」组合，都要问一句——**被挡下时，这把「未完成」记在哪？**

### 案例 4｜「认身份靠 CWD」的两个连环坑

- **症状 1**：某人信箱里多了一条「续窗提示」，但他根本没被拉过；另有人**所有**被自动拉起的窗都收不到补课提示。
- **根因**：续窗提示脚本用 `process.cwd()`「认本窗」。而开窗器调用它时不切目录：
  - 机器（叫醒器）在别的工作目录拉窗 → 认不出窗 → **静默不发**（还叠了一个 `| Out-Null` 把报错吞了）＝**出厂就有**的 bug；
  - 人手动从自己目录拉别家的窗 → 提示投到**操作者自己**的信箱。
- **修法**：开窗脚本显式传参 `--窗 <名字>`（与工作目录无关）；路径解析全部归一化。
- **验证**：干看证明旧式命中错人、新式命中目标窗；真机 E2E：从 A 的目录拉 B 的窗 → 提示落进 B 的信箱（1→2）、A 的信箱没污染。
- **记住什么**：**认身份别靠工作目录**——CWD 属于调用环境，不属于目标；**别用静默吞报错**（`| Out-Null`），这条要是没吞，第一周就会暴露。

### 案例 5｜动作会顺手改状态，基线要在动作之后重新量

- **症状**：拉窗成功后约 0.8 秒，「续窗提示」信才被开窗器追进该窗信箱；而拉窗那一刻记的字节游标没算上它 → 下一轮被当「新信」→ 防刷挡下（游标不动）→ **3 分钟后又白拉一次**。
- **修法**：拉窗成功后**按拉完后的真实字节重记基线**（私信信箱＋收件箱都重记）。该窗已开，期间到的信它自己会读，重记是安全的。
- **验证**：投信 → 拉窗 → 游标＝文件当前字节（含提示）✓；关窗＋过防刷期 → **没有**第二次拉窗 ✓（旧版此时必白拉一次）。
- **记住什么**：**「动作会顺手改状态」时，基线要在动作之后再量**——拉窗会投提示、投信会改游标，都属于这一类。

### 案例 6｜排期环：窗关着也别漏活

- **问题**：窗口是按需开的、闲置自动收。**窗里挂的定时任务只在窗活着时才会响**——窗关着，到点就静默漏掉（真实漏过：账单提醒环、月度续期环）。
- **做法（登记表＋执行者）**：
  - **一张登记表**：各窗把「到点的活」写进自家 `.state\叫醒环.json`：
    ```bash
    node 环.cjs 加 --id 充卡 --文 "到点了（每月5号）：提醒充卡……" --每月 5 --时间 10:00
    # 每天 09:30 ｜ 每周 一,四 --时间 09:30 ｜ 每年 4,10 --日 8 --时间 10:00 ｜ 一次 "2026-11-16 10:00"
    node 环.cjs 列 / 删 --id 充卡 / 查
    ```
  - **一个执行者**：那个**唯一常驻的家伙**（叫醒器）每轮扫各窗登记表；到点就**投一封「【排期环·id】文」进该窗私信箱 → 拉窗 → 该窗收信照做**。链路全走已有的私信/拉窗设施（0 新机制）。
- **语义（边界都要测）**：
  - 同一周期只投一次（触发键＝周期日期，存在执行者状态里）；
  - 机器关机睡过的：容忍期（默认 12 小时）内开机**补发**，信里标「（补发：本应 …）」；超容忍跳过并记账；
  - **登记前的旧点不追发**（条目带「登记时间」）——新登记的环不会一上来就把今天已经过去的点补一遍；
  - 坏档/乱写都不崩，最多这条不干。
- **验证**：算到期 11 例（含「今天还没到点取上周」「每月 31 号遇 2 月」「3 月取去年 10-08」）＋ 一轮 19 断言 + 不重投/补发/超容忍/不追旧/坏档不崩——**35 项全过**；生产实测到点自动投信留痕。
- **记住什么**：
  - **定时活别挂在「按需存在」的东西里**（窗会关、会话会死）；把「到点」交给唯一常驻者，业务窗只管「收到就干」。
  - **登记类系统必须有「登记时间」语义**，否则新登记的周期环会立刻追发上一个刚过去的点。
  - **周日历/月历别信直觉**：写 6 个边界用例才把「每周一早上 9 点查、但今天是周一 8 点」这种算对。
  - 多文件工具铺给各窗时**依赖要一起铺**；调用方再加一道「本地没有就找核心目录」的回退（曾漏铺一个模块 → 各窗 `MODULE_NOT_FOUND`）。

### 案例 7｜收窗杀了后台活：「有活干就不收」

- **事故**：某个员工修任务跑到一半，她的窗「闲置 31.6 分钟」被自动收窗——连同窗里 Monitor 正跑的 worker 一起杀了。证据：报告只剩 2 字节（中断符）、工作树 29 个文件半成品未提交、进度文件空、worker 进程消失。
- **根因**：收窗规则只看：会话闲置 ≥30 分＋无未读＋非刚拉/刚开——**没有看「窗里有没有正在跑的活」**。而窗里挂的 Monitor（后台长命令：worker、构建、盯梢）**不写会话文件** → 窗口「看起来」闲置，实际在干活。
- **修法**（收窗前置检查）：
  - 查这扇窗的**后代进程**（一次 PS 全表拿 ppid 链）；除「标准被动监听」白名单（跟读监听、守护、心跳、告警喇叭……）外还有别的在跑（node/bash/python…）→ **不收**，日志记「有活干…先不收」。
  - 只剩被动监听 → 照旧（闲置 30 分＋无未读）可收。
  - 两颗防误判钉子：①**出生时间断链**——Windows 父 pid 会回收重用，子进程出生时间比父早（>2 秒）＝断链，不认；②**同窗多名字去重**——有的家目录里有与信箱同名的子目录，同一扇窗会被两个名字各判一遍，只判第一次。
- **波及面（同日审计）**：另一起同类——盯梢 Monitor 随窗被杀（status=error），靠排期环把她拉回来接上——**排期环兜底有效**。
- **记住什么**：「按需收窗」省资源的前提是**先分清「闲着」和「在后台干活」**；Monitor/worker 不写会话文件，别只看时戳。后台活尽量登记排期环做兜底。

### 案例 8｜开机自检被私信顶掉：启动期的竞态与修复

- **症状**：早上开机/被叫醒的窗口「听不见消息」——人醒着、监听链没挂、消息躺着没人看。中招 4 个窗，**共同点：被拉起时信箱里有未读私信**。
- **根因**：AI 运行时的**启动提示**在「会话开始」之后才提交；而收信扩展在「会话开始」事件里抢先把私信投成一轮 → 启动提示再来时已「正在处理中」；不带排队参数的投递会**抛错**（界面一闪而过）→ **自检被丢弃**。于是窗口只处理了私信，没跑自检（挂链、查漏全没做）。
- **修法**（收信扩展）：
  1. **让路**：本会话第一次投放前，轮询「空闲」状态，等启动提示的回合先开跑（最多 10 秒；等不到就当没有启动提示，直接投）。
  2. **投放统一带「排队」语义**：空闲时直接开一轮；正在流式则排队——**两种情况都不丢**。
  3. 「会话开始」里**不 await** 让路逻辑（若 await 会堵住启动流程，反而死锁）。
- **验证**：竞态回归测试（假运行时＋可切换的「忙/闲」）14 项全过；真机 E2E：新会话**第 1 条＝启动自检、第 2 条＝私信** ✓（修复前是反的）。
- **怎么查谁丢了自检**（留作巡检手段）：看会话文件的第一条用户消息出现「开机自检」＝正常，出现「【私信】」＝丢了；看进程树：窗在跑但没有监听进程＝没挂链。
- **记住什么**：**会话启动期做注入的扩展，要让「启动提示」先跑**；投递消息宁可**排队**，别和启动提示抢跑。竞态类修复要**有回归测试**——把「忙/闲」做成可切换的假对象，才能稳定复现场景。

### 案例 9｜第二扇窗把老窗的唤醒环退役了（单实例守卫 v2）

- **事**：测试时直接跑了生产开窗脚本 → **同一个员工被开了两扇窗**；新窗恢复同一份会话时，运行时把该会话的**唤醒环退役并删除**；测试窗随即关掉，老窗继续跑——监听在、进程活——**但环没了**：收件箱再响也没有东西去唤醒它。
- **后果**：老板两条消息到了，老窗**毫无反应**；13 分钟后靠看门狗重开窗才补课。而**链体检当时是「假绿」**：它只查「进程在＋监听在」，看不见「环没了」；看门狗也一样（进程在＝健康）。
- **修法**：
  1. **单实例守卫 v2**：同目录只要有**活着的 AI 进程（不限年龄）**就拒绝开第二扇（v1 只防「刚刚才开过」）。
  2. 看门狗：窗口活着就把「连败」计数清零（防跨天累计误报）。
  3. **启动单故障对策**：出现「环被退役」→ **立刻补挂唤醒环**。
  4. 同步排除名单补「整机单例」工具——不再往各窗推。
- **验证**：活窗时守卫放行拒绝、打出 SKIP；空目录正常放行；试验目录全验。
- **记住什么**：
  - 「续窗提示」只救**被拉起的新窗**（它读信补挂环）；**留在原地没死的窗，没人提醒它**——所以绝不要主动造出「两扇窗」这个局面。
  - 链路三件套缺一不可：**守护＋监听＋唤醒环**。

#### 补记（2026-10-18，聊天质检专员·宁中则 实测，木婉清收）：监听挂了＋环被退役，会同时发生

- **事**：Monitor（跟读收件箱）异常退出 `exitCode 3221225786`＝`0xC000013A`（**被 Ctrl+C / 终端中断，不是崩溃，别去查代码**）；**同时** Loop #1 被「会话恢复」退役删除。两条一起没了。
- **危险点**：光看其中一个会以为只是「没新消息」——监听没了不报错，环没了不报错，**链断了但看起来一切正常**。
- **判据（两个同时满足 = 链断了，立刻补）**：
  1. `MonitorList` → `status=error` 且 `outputLines=0`；
  2. 会话里出现 `retired during session recovery and was deleted`。
- **补法**：重挂 Monitor ＋ 重挂事件环（`monitor:output`），两件都要补，只补一个等于没补。
- **出处**：宁中则 2026-10-18 本窗实测（断后自补，台账已记）。

### 案例 10｜三个「静默小坑」连环三坑

- **10a 空名假命中**：在错误目录（套件目录里）跑工具 → 「认本窗」失败 → 窗名成了空串 → 「找家」逻辑用 `join(根,"")`＝**根目录本身**（真实存在！）→ 于是：查＝读到不存在的空档报「0 条」；写＝**静默把档写进根目录**（永远不会被扫到＝登记了也永不触发）。
  - 修法：认窗多认两种跑法；**空名直接拒绝**；「找家」必须认**特征文件**（套件标记）而不是「目录存在」；认不出时**明确报错、非零退出**，不再静默。
  - 验证：正确目录三场景全对；错误目录明确报错、exit≠0、**不落盘**。
- **10b 互锁自锁**：防撞车逻辑把「任何进程命令行含某任务名」都算「有任务在跑」。平时错峰没问题；但**电脑夜里关机、次日开机时任务计划把漏掉的 16 个任务在同一秒全部补跑** → 16 个脚本互相看见 → **全部跳过**（谁都没干，一晚上白过）。
  - 修法：防撞车**只认「本窗」**（进程命令行必须同时含本窗根目录）；列进程的输出**强制 UTF-8**（否则中文路径在 GBK 控制台里匹配静默失灵）。
  - 验证：同窗假进程 → 跳过 ✓；别窗假进程 → 正常执行 ✓。
  - 记住：**「进程在不在」式互判一定要限定范围**；**跨进程通信的编码要定死**，别赌环境默认码页。
- **10c 子串匹配假命中**：单实例守卫用「命令行包含 `叫醒器.cjs`」判断已在跑——结果把**「装叫醒器.cjs」**（含子串）也当成了已有实例 → 重启时新实例静默不启动。
  - 修法：匹配加**路径分隔符边界**（`(^|[\/\s"])叫醒器[.]cjs`），Node 侧和隐藏壳脚本侧**都改**。
- **记住什么**：**子串匹配当进程/文件身份判据不可靠，必须加边界**；「空值不要只用 exists 兜底」；「出错要大声」。

## 四、验收清单（搭完体系，自己出三关）

1. **杀常驻**：杀掉叫醒器/守护 → 5 分钟内被巡查自动拉起。
2. **造假故障**：哨兵演练模式 → 告警端到端到达（谁收、多久到）。
3. **关窗投信**：关着窗投一封信 → 自动拉起、补读、回信。
4. **环退役**：手动制造「环没了」→ 有东西能发现并补挂（没有就先补上这个检查）。
5. **重启全机**：所有常驻/监听/任务自动恢复，无一项靠手动。
6. **断网**：长连接重连、补拉停机期间的消息，不丢。
7. **挡下不吞**：在防刷窗口内投信 → 当场不拉、**下轮必拉**（游标没被吞）。
8. **有活不收**：窗里挂一个后台任务 → 闲置 30 分钟**不能**被收窗。

## 五、配套工具：`工具\自巡查.cjs`（通用巡查器）

「定期巡查＋不在就拉起」（原则 2）的通用小工具，配置驱动、本机实测：

```bash
node 自巡查.cjs                 # 跑一轮：不在的拉起，不新鲜的记警
node 自巡查.cjs --干看           # 只报告不动作（试配置用）
node 自巡查.cjs --配置 我的巡查.json
```

配置（同目录 `自巡查.example.json`）：

```json
{
  "log": "自巡查.log",
  "tasks": [
    {
      "name": "叫醒器",
      "match": "(^|[\\\\/\\s\"])叫醒器[.]cjs",
      "exe": "node",
      "args": ["D:\\path\\叫醒器.cjs"],
      "hide": true
    },
    { "name": "清理任务", "match": "清理[.]cjs", "exe": "node", "args": ["D:\\path\\清理.cjs"], "staleLog": { "path": "D:\\path\\清理.log", "maxAgeMin": 120 } }
  ]
}
```

- `match`：进程命令行正则（**记得带边界**，别用裸子串——案例 10c）；
- `exe`/`args`/`hide`：不在时的拉起方式（隐藏窗口）；
- `staleLog`（可选）：进程在、但日志超过 N 分钟没动 → 记「疑似卡死」警（不自动杀，防误伤）。
- 每次任务由 Windows 计划任务每 5 分钟调一次即可（注册方法见《企微 AI 员工体系-从零搭建》的隐藏壳套路，或任意你熟悉的定时器）。

**本机实测记录**（2026-10-14）：配套 `测试\冒烟测试.mjs` 独立复跑 **12/12 全过**——覆盖：无配置报错、非法正则报错、干看报不在、真跑自动拉起、边界防误命中（「装假常驻.cjs」不骗带边界规则）、卡死检查（日志超时记警）、日志生成与滚动。命令：`node 测试\冒烟测试.mjs`。
