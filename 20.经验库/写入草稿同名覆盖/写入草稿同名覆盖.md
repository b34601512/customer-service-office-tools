# 写入草稿同名覆盖：`runtime/写入-*.json` 不是行数凭据

> 一句话：**草稿文件只记「最后一次写入」，不记「这一单写了几行」。**行数一律回读在线表（目标列计数），草稿最多当线索。

## 现象

同一任务目录里用固定文件名落写入草稿（`runtime/写入-<店>.json`、`写入-<单号>.json` 里只写店名不带单号）：

- 跨单、跨批次连跑时，后一次运行**原地覆盖**前一次，目录里永远只剩一份；
- 于是「按草稿数行数」＝只看得到最后一段 —— 一单本该 8 行，草稿里只剩 3 行；或者把上一单残留当成本单的行。

它不报错、退出码照样 0、回读也可能「对上」（因为回读比对的是最后一次草稿，不是整单），**错得静默**。

## 判据（怎么当场认出来）

- 草稿文件的 mtime 与本次运行的开始时间不符，或内容和刚跑的那一批对不上；
- 草稿行数 < 表内实际新增行数（尤其表里连着几行都是同一单号时）；
- 同一目录下 `写入-*.json` 只有一份，但今天跑过不止一次写入。

## 改法（照抄）

1. **验收只认表**：行数/内容以在线表回读为准（目标列计数、必要时连 dataSha256 一起），不拿草稿当凭据。
2. **要留草稿就换唯一名**：路径里带单号或时间戳（`runtime/写入-<单号>-<yyyyMMddHHmmss>.json`）；固定名只留「最后一次状态」，不当历史。
3. **登记/交接表**写行数时注明出处：写「读表 C 列计数」，不写「按写入文件 N 行」。
4. 已经踩过的同类：`/tmp/patch.json`（全公司窗口共用同一文件名，`gh api --input` 返回成功但发出去的是别人的内容）——根因同一条：**固定名临时文件＝共用一块白板**。

## 验证

- 重跑一次写入：草稿文件 mtime 与行数应变化，表内目标区应不变（不会重复写）；
- 用表回读的行数复核交接表登记的数字，两者必须一致。

## 出处

2026-11-16 天猫2 `5127916465016113516`（10902–10904 三行）与抖音5 `6931494558356569505`（表① 3029–3036 八行）收口时发现：`runtime/写入-*.json` 同类文件同名覆盖，只剩最后一次写入；结论改为行数一律读表核（C 列计数）。
