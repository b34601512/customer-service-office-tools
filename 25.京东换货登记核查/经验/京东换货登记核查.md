# 京东「上门换新取件」登记核查（2026-09-27 用户交代 + 实测）

## 一、业务是什么（为什么要查）

京东有一种售后叫**上门换新**：京东仓**直接把新机换给客户**（平台上会生成一张 ¥0 的换新订单，
买家备注写「售后上门换新：服务单号 xxx #上门换新#原订单号 xxx」，商家备注写「时出发上门换新」）。
但客户那台**故障机仍要寄回我们工厂** —— 所以客服必须在金山
[《2026年【湖南怀化售后】对接表》](https://www.kdocs.cn/l/ccj1mhG3wLy6) →「**换货维修登记表**」补一条登记，
工厂才知道这台机器是谁寄回的。

**不查会亏机器**：如果客服登记成了「换新」又填了客户地址，工厂看登记可能**再寄一台**出去 → 重复换货、白亏一台。

**规范登记的形态**（用户口径）：
- 「处理方式」= 常见「收到后直接入库。我已经给客户提前换出了」
- **质保标准 / 客户寄给厂家的运费 / 厂家寄给客户的运费 三项都选「无需处理」**
- **客户地址列不填**（填了 = 工厂可能照着寄）
- 备注常写「客户申请了上门换新」

## 二、京东侧怎么取（实测细节）

入口：交易 → 售后管理 → 自主售后 `https://shop.jd.com/jdm/trade/after-sale/independent-after-sale/list`

1. 点「**全部**」tab（默认在「待审核」，不切会 0 条）；
2. 点「**展开**」（切完 tab 筛选区会自动收起，要重新点，否则找不到「售后状态」等筛选项）；
3. 筛：**客户期望 = 换货**，**售后状态 = 完成**（页面默认最近 3 个月）；
4. **「上门换新取件」只能本地筛**：
   - ❌ 不是商品名称（在「商品名称/编码」里搜「上门换新取件」→ 0 条，实测）
   - ❌ 不是服务标签（服务标签里叫「**可能上门换新**」，不是同一个东西）
   - ✅ 是每行响应里的 `pickWareFacetDTO.pickWareTypeName == "上门换新取件"`（同一行还有
     `pickWareStateName`=取件状态、`approveFacetDTO.approveResultName`=「上门换新」）
5. 窗口默认取 **3 个月**（用户 2026-09-27 拍板「改成 3 个月」；页面默认范围就是 3 个月），
   在本地按 `serviceOrderBaseFacetDTO.afsApplyTime` 裁。

响应里其它有用的字段：`orderFacetDTO.vendorRemarkFacetDTO.remark`（商家备注，客服写「已提前发出」）、
`mainWareFacetDTO.wareName`、`receiveFacetDTO.afsServiceId`（售后单号）。

坑（同 24号 经验）：筛选控件必须**真实鼠标点**（JS `el.click()` 打不开下拉）；
接口 `dsm.seller.afs.bff.serviceOrderQueryDsmService.page` **带签名**，页内 fetch 被拒 code 312 → 只能驱动页面。

## 三、金山侧怎么读（表 2.8 万行，网页读不全）

- 「换货维修登记表」共 **2.8 万+ 行**，网页端 `getUsedRange().getRangeContents()` **只读得到前 1.85 万行**
  （滚到表尾也没用）→ 最新登记（行号 27xxx-28xxx）根本读不到。
- 所以走 **AirScript 按订单号查**（`src/tools/kdocs-query.js` 那套；批量 10 个关键词/批稳，20 个/批 403）。
- ⚠ **老脚本（2026-09-27.1 及以前）只返回非空单元格 → 列位置丢失**，
  判不了「地址列是不是空的」；**2026-09-27.2 起每行多返回 `cells: [{c:列号, v:文字}]`**，才能按列号精确判。
- 表列号（0 基）：0 时间、1 产品名称、2 型号、5 数量、6 店铺、7 客户 ID、**10 地址**、12 购买日期、
  **13 订单号**、14 现象描述、15 问题分类、**16 处理方式**、**17 质保标准**、**18 客户寄给厂家的运费**、
  **19 厂家寄给客户的运费**、20 售后周期、22 处理客服、23 备注。
- 客服登记的是**服务单对应的订单号**（=京东列表里的 `orderId`），不是换新订单号；
  别拿截图里「原订单号」去猜——实测两种写法都能对上（例：3594409015225289 既是原订单号也是 orderId）。

## 五、金山脚本怎么办（2026-09-27 用户拍板：别把老脚本越写越臃肿）

用户明确「不想一个脚本写得冗长」→ **新建一份专用的短脚本**，老的「只读查询订单号」保持不动：

| 脚本名 | 用在哪 | 特点 |
| --- | --- | --- |
| 只读查询订单号（老，2026-09-27.1） | 22号/24号：跨多表关键词查单 | 只返回**非空值**（列位置丢失） |
| **只读查行带列号**（新，2026-09-27.3） | 25号：指定单表按单号查行 | **返回 `cells:[{c:列号,v:文字}]`**，能判「地址列空不空」 |

新脚本 webhook 填 `project-config/kdocs-airscript.json` → `scripts.rowQuery.webhookUrl`
（`src/engine/kdocsAirScript.js` 的 `options.script` 切换）；没配就自动退回老脚本并在报告里标「粗判」。

**实战结论（必看）**：同一批 12 单，老脚本粗判「12 单全规范」，新脚本按列号一看 ——
`3558494018774110`（行 27378）**质保标准空着**、处理方式写的「换货」。**粗判不能出结论，只能当初步筛查。**
