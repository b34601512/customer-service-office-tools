# 项目说明

## 1. 项目目标

这是一个统一的发票自动化工具箱：巡检京东待开票和催票订单，从诺诺发票系统按订单号取得发票，再把发票回传到京东、天猫、拼多多或抖音。根目录 `tui/总入口TUI.js` 是统一总控制台：首页只展示子项目入口可用性和下载中心登录状态，店铺/订单明细进入各平台控制台查看；各平台仍保留独立配置、登录态、日志和凭证，单个平台出错不会把整套工具搅在一起。

## 2. 技术形态

- Windows 本地 Node.js 程序，全部采用 CommonJS；各子项目用 Playwright 控制 Edge/Chrome。
- 日常管理界面是命令行菜单；通用下载中心另提供本机 HTTP 接口。
- 配置和任务状态使用 JSON，订单导出表为 XLSX/CSV，发票主要为 PDF；测试使用 Node.js 自带测试器。

## 3. 模块结构

- `总入口.js`、`共享CLI/`、`tui/总入口TUI.js`：五个业务子项目的启动菜单、只读状态汇总、通用表单、店铺选择、分页订单队列、独立业务视图和会话日志页。`共享CLI/平台状态汇总.js` 只读取各平台 `data/` 摘要，不写业务数据；`共享CLI/tui/镜像表格.js` 负责把店铺和订单镜像渲染成固定列表格；回传平台在提供订单读取函数时会增加「2订单」全量订单页，店铺页回车仍可查看单店订单明细。
- `共享订单状态/`：1/2/4/5/6 共用的四阶段规则与持久仓库；各平台数据仍保存在各自 `data/`，不写入中央订单文件。
- `共享发票回传/`：2/4/5/6 共用的“只消费发票已登记”、逐单进度、多店失败继续和汇总规则。
- `1.京东开票巡检/`：读取京东开票治理页面或接口，对比历史快照，新增异常时生成截图、报告和桌面通知。
- `2.京东发票回传/`：扫描催票申请，维护订单处理状态，并批量下载、上传京东发票。
- `3.通用发票下载中心/`：管理诺诺登录，先复用本地发票，缺失时跨开票主体查询下载，并维护订单号到文件的索引和 HTTP 服务。
- `4.天猫发票回传/`、`5.拼多多发票回传/`、`6.抖音发票回传/`：按店铺保存浏览器资料，导出待开票订单，调用下载中心后逐单上传、提交并截图。
- 各子项目的 `src/` 是业务代码，`tests/` 是测试，`data/` 和 `runtime/` 保存本机数据。

## 4. 数据流

平台后台或京东接口产生待开票订单 → 子项目只读同步到本平台订单仓库 → 人工按“待处理 → 处理中 → 发票已登记 → 已处理”推进 → 正式回传只消费“发票已登记” → 本机下载中心按订单号返回发票文件 → 对应平台上传并正式提交 → 成功自动进入“已处理”，跳过或失败仍留在“发票已登记”以便重试。

三类状态不得混用：`workflowStatus` 是人工阶段，`platformStatus` 是只读的平台事实，`lastReturnAttempt.status` 是某一次回传进度。3 号下载中心只维护订单号与发票文件的对应，不提供人工订单状态菜单。

CLI 标准输出只承载当前业务页面；底层 `console.*` 诊断及兼容的 TTY 原地刷新进度会在会话内进入独立日志缓冲，首页按 `L` 分页查看。嵌套菜单、订单队列、订单详情、任务进度和结果汇总均清屏后重绘，禁止把函数入口追踪或逐单长明细直接追加到业务页面；多店最终结果页最多列出 10 家，其余明细进入日志页。

## 5. 如何运行和测试

双击 `启动发票自动化.bat`，或运行 `node .\总入口.js`。首次使用应进入所需子目录执行 `npm install`，以后用该目录的启动批处理或 `npm start`。

根共享层运行 `node --test .\总入口.test.js .\共享CLI\*.test.js .\共享CLI\tui\*.test.js .\共享订单状态\*.test.js .\共享发票回传\*.test.js .\tui\*.test.js`；每个子项目进入目录执行 `npm test`。自动测试全部使用临时 JSON、模拟页面或模拟回调，不执行真实登录、发票下载、上传或提交。人工验收见根目录 `订单状态人工验收.md`；正式回传会提交真实发票，已按用户决定移除 CLI 确认闸门，进入回传即直接执行，不再要求输入 y 确认。
