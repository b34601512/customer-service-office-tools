# Issue 001：正式回传被浏览器占用拦截

## 意图

真实复现拼多多发票回传失败，依据运行证据定位根因并修复；不以兼容、强制兜底或绕行掩盖生命周期设计问题。

## 背景与已采集证据

- 2026-08-31 的订单记录显示，订单 `240515-580837742083169` 正式回传未进入下载/上传阶段。
- 直接错误：对应店铺资料目录仍被多个 Edge 进程占用，程序要求人工关窗后重试。
- 同次运行日志显示两家店铺登录成功并把业务浏览器留在前台。
- `同步拼多多待处理订单` 与 `执行拼多多发票回传` 的 `finally` 都有意不关闭自己创建的浏览器上下文；下一动作又拒绝同资料目录存在浏览器进程。
- 共享工作台的唯一公开回传动作固定先执行同步、再执行正式回传；两阶段使用同一店铺资料目录。
- Git 历史确认：2026-08-25 曾把同步阶段原有的 `await context.close()` 改为保持窗口，现有测试同步改成断言不关闭；这正是失败开始存在的回归点。
- 根因确认：同步阶段泄漏了自己拥有的浏览器上下文，随后正式回传按并发保护规则正确拒绝同资料目录的第二个实例。

## 验收清单

- [x] 完整阅读登录、同步、正式回传、浏览器上下文与共享闸门调用链。
- [x] 用现有运行记录、调用顺序与变更历史确认根因。
- [x] 修复后，同一程序内的正常操作顺序不会被自己遗留的浏览器阻断。
- [x] 不允许同一店铺资料目录并发启动两个浏览器实例。
- [x] 正式回传仍经过唯一业务入口和正式回传闸门。
- [x] 自动化测试 76/76 通过。
- [x] 真实只读链路验证：03店同步读取 1 单；同步后进程为空；同资料目录立即重新接管成功；关闭后无残留进程。
- [x] 获得口令 `161323` 后执行真实正式流程：2 家店共 3 单全部到达下载中心，0 程序错误；3 单均因诺诺暂无已开具发票而按规则跳过并留存截图，当前没有可进入上传/确认分支的发票。

## 最终结果

- 原“同步留下浏览器、正式回传被自己拦截”故障未再出现。
- 02 店读取 2 单、03 店读取 1 单；正式流程结果为成功 0、业务跳过 3、程序失败 0。
- 三张凭证均存在；抽查画面确认订单仍在拼多多“待开票”，承诺开票期限尚未到。
- 本次流程创建的两组店铺浏览器已按专用资料目录关闭，当前无残留，不会阻断下次运行。

## 边界

- 不牺牲多店铺账号资料隔离、登录验证及正式提交确认。
- 不强杀来源不明或用户正在使用的浏览器进程。
- 不新增第二套状态真源、兼容分支或长期兜底。
- 不修改同仓库其他项目及其未提交工作。
