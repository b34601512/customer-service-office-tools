# Issue 009：回传阶段店铺身份识别/切店不稳（顶部店铺ID 读不到）

## 意图

让「回传阶段」能稳定识别当前店铺并切到目标店，不再出现 `读取抖音当前店铺 ID 失败：顶部店铺信息识别到 0 个有效店铺 ID`。

## 背景与证据

- 规律（2026-09-20 三次，均在同一位置）：
  - 12:00:51 店铺3、12:35:25 店铺3、12:41:06 店铺3：`[店铺] … error｜读取抖音当前店铺 ID 失败：顶部店铺信息识别到 0 个有效店铺 ID。`
- 12:49 截屏取证：页面完全正常（`/ffa/morder/receipt/list`，待开票 1 单 6955060045796152564 ¥1167.00），右上店铺面板已展开且**明摆着 `店铺ID 29502951`** —— 说明不是页面问题，是读取/时序问题。
- 同一轮里同一代码有时成功（12:41:15 店铺5 同步成功、12:35 店铺3 同步成功），说明是时序性缺陷。
- 次生现象：回传阶段各层超时叠加（goto 60s + 待开票列表 120s + 身份读取 15s+10s + 切店 3×~30s + 等目标店 120s）合计 ~8 分钟才失败，期间日志只有进度提示。

## 待查方向（先取证，不许猜）

1. `读取当前抖音店铺ID` 依赖 `shopHeader.locator(':scope [label="店铺ID"][value]')`；`读取抖音店铺名` 依赖 `:scope > [data-bytereplay-mask="true"]` 唯一可见。失败时把 `shopHeader` 的 outerHTML / 可见文本 / 页面地址落盘到 `runtime/`，对比成功与失败两种 DOM。
2. `等待目标店铺` 的内层 `for (pages)` 没有截止时间判断，多页签时会拖长单次外层循环（需要每页前检查 deadline，并给轮询用的身份读取传更短超时）。
3. 进入切店前先收敛多余页签（保留保活页）。

## 验收清单

- [ ] 失败现场落盘（DOM + URL + 页签数），能用失败样本解释 0 个有效店铺 ID。
- [ ] 根因修复 + 反向断言测试（锁死「面板已渲染出店铺ID 时必须能读到」）。
- [ ] 全量测试全绿。
- [ ] 真机：连续两轮跑 `printf '6\na\n' | node src/cli/startCli.js`，两家店回传阶段都不再出现该错误。
- [ ] 收窄超时叠加：任一阶段失败的整体耗时 ≤ ~2 分钟。

## 边界

- 不改店铺身份校验强度（仍要求 storeId + storeName 双匹配）；不加模糊兜底。
- 不重复请求平台数据；需要人工（短信/滑块）时停下叫用户。
