# Issue 007：报表落盘依赖承载页面，页面自关导致同步失败

## 意图

根治抖音「下载报表」在承载页面自行关闭后落盘失败的问题；落盘不再依赖页面/blob 存活。

## 背景与证据

- 现象（2026-09-20 两次同现象，店铺3 同步阶段）：
  `下载报表落盘失败（文件名=order_invoice_export_task_id_*.xlsx，来源地址=blob:https://fxg.jinritemai.com/…，当前页面列表=空）：浏览器原生落盘报“download.saveAs: Target page, context or browser has been closed”；直取字节失败：apiRequestContext.get: Target page, context or browser has been closed`
- 取证（一次性诊断脚本，已删）：
  - 报表真实来源是 `GET https://fxg.jinritemai.com/order/invoice/download?task_id=7687426398369202484&…`（HTTP 200，`content-type: application/download`，7893B，`PK` 头=xlsx），脚本在响应到达时当场截获字节；
  - 同一秒 context 级捕获到 `CTX_DOWNLOAD url=blob:https://fxg.jinritemai.com/…`；
  - 约 4 秒后承载页 `report-list` 触发 `PAGE_CLOSE`，因它是唯一页面，紧接 `CTX_CLOSE`；
  - 随后 `download.saveAs` 与 `context.request.get(blob)` 双双报 context closed；
  - Windows 应用日志无 msedge 崩溃记录 → 是页面自关，不是浏览器崩溃。
- 根因：抖音报表先走 HTTP，再由承载页转 blob 下载；承载页面自行关闭后 blob 失效，而旧方案（context 级捕获 download + 立即 saveAs；失败后 `context.request.get(blob)`）都依赖页面/blob 存活。

## 修复

- 新增 `捕获抖音报表响应(context)`：点击下载**前**挂 context 级 `response` 监听；命中 `/order/invoice/download` 或 xlsx 类 content-type 时**立即**读取响应体存入内存。
- 新增 `选取本次报表字节(命中列表, download, 开始时间)`：按导出任务号（文件名 `task_id_<id>` ↔ 地址 `task_id`）精确匹配，否则退回点击后最后一条。
- `下载最新抖音导出报表` 落盘顺序：`saveAs` → **同一次下载的响应字节** → blob 直取；响应监听在函数收尾统一停止。
- 不是重复请求平台数据：使用的就是本次下载本身的那一份响应体。

## 验收清单

- [x] 识别规则：`/order/invoice/download` 或 xlsx 类 content-type 命中；导出任务列表 JSON 不误收。
- [x] 响应到达即抓字节；按任务号精确挑选；收尾摘掉监听（无泄漏）。
- [x] 源码顺序断言：先挂监听再点击下载；落盘失败先响应字节、后 blob 直取。
- [x] 单文件 9/9、项目全量 113/113 通过。
- [x] 真机验证：12:19 跑，店铺3 同步成功（导出文件 7893B = 捕获字节数；日志显示 `/order/invoice/download` 200 application/download 已读入 7893B）。本轮 saveAs 恰好成功故未走回退分支。

## 边界

- 不改店铺身份校验、不动登录资料、不强杀浏览器。
- 只改落盘取字节方式；报表内容与解析规则不变。
