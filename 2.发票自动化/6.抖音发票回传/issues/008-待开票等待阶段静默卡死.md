# Issue 008：待开票等待阶段静默卡死（无超时的 Playwright 调用）

## 意图

杜绝「既没输出也没报错」的长时间卡死：抓取/等待路径上所有可能永不返回的 Playwright 调用都必须有墙钟上限。

## 背景与证据

- 现象（2026-09-20 12:19:44 起，首次实锤）：店铺3 同步成功后进入回传阶段，进度提示 `正在打开抖音待开票列表：…已等待 N 秒` 一直递增到 12:33（约 13 分钟），期间**无任何超时或报错**，最后靠人工停掉。
- 现场截屏取证：页面完全正常（`/ffa/morder/receipt/list`，待开票 1 单：6917794627678514923 ¥538.00，就绪三要素齐全），无滑块、无登录页、进程无死循环 CPU 占用。
- 根因：等待循环把超时写在 `while (Date.now() - startedAt < timeoutMs)` 的**条件**里，但循环体调用的 `page.evaluate` / `evaluateAll` / `keyboard.press` 在渲染进程无响应时**永远不返回**（Playwright 这类调用没有默认超时），循环体卡住 → 条件判断永远走不到 → 静默卡死。违反铁律 #3（禁止静默等待）。

## 修复

- `src/browser/dynamicWait.js` 新增 `限时等待(承诺, { 超时毫秒, 说明 })`：`Promise.race` + 墙钟上限，超时抛 `…超过墙钟上限 N 毫秒仍未返回，按卡死处理。`（原始错误正常透传）。
- `src/invoiceReturn/douyinInvoicePage.js`：
  - `关闭抖音非业务浮层(page, 选项)`：`keyboard.press('Escape')`、`page.evaluate(...)` 全部包进 `限时等待`（默认 5s / 10s，可注入）。卡死时兜底返回 `[]`，让外层循环继续判断页面状态。
  - `检测抖音滑块验证(page, 选项)`：`locator(...).evaluateAll(...)` 包进 `限时等待`（默认 10s）。卡死时兜底返回 `false`。
  - 导出 `检测抖音滑块验证` 供测试使用。

## 验收清单

- [x] `限时等待`：永不返回 → 按上限报错；正常返回/原始错误透传；耗时受控。
- [x] 假页面（evaluate / evaluateAll 永不返回）：`关闭抖音非业务浮层` 必须限时兜底 `[]`、`检测抖音滑块验证` 必须限时兜底 `false`，均 < 2s 返回。
- [x] 源码反向断言：待开票等待路径内不允许出现未包上限的 `page.evaluate`；键盘与滑块求值必须走 `限时等待`。
- [x] 全量 `npm test` 117/117 通过（含新增 4 条）。
- [x] 真机验证：12:35:10→12:35:25 同一位置 **15 秒内给出明确错误**（对比 12:19 的 13 分钟静默）——无限悬挂已消除。遗留：各层超时叠加时仍要 ~8 分钟才失败（见 issues/009）。

## 边界

- 只加墙钟上限与兜底，不改业务流程与判定条件；不因为限时而跳过正常状态判断。
- 不改「滑块必须人工」的红线：限时只针对「求值卡死」这一缺陷路径。
