# 16号项目采集中退出未保存结果

## 意图与背景

用户要求进一步审查 v10 交付风险。本轮仅诊断，未改生产代码及发布包。
正在采集时按0或Ctrl+C会立即退出；已完成页面的数据仍只在内存，存在丢失本次结果的实际风险。

## 证据

- boss_tui.py:429 使用 daemon=True 任务线程。
- boss_tui.py:884 退出只 stop + cleanup，没有停止任务并等待保存的流程。
- boss_cdp.py:918 在整个分页循环结束后才 export_rows。
- 离线定向复现：第一页返回数据、第二页阻塞时，export调用0次；正常结束后1次。任务线程确认为daemon。未终止真实采集进程，未操作浏览器。

## 验收清单

- [x] 阅读退出、线程、分页与导出完整链路并复现保存时机。
- [x] 设计一个统一的停止/保存流程或阶段性保存策略，保护正常退出时的已采集结果。
- [x] 验证采集中退出保留结果，空任务退出正常。

## v0.10处理

TaskRunner使用停止事件和非daemon线程；0/Ctrl+C请求停止后保持界面刷新，业务完成导出才关闭浏览器和程序。退出等待期间不再允许启动新任务；保存失败留在日志页。
停止事件经run_fetch、fetch_page、enrich_company_names传递，停止列表等待、下一条详情和下一页；已经完成的当前页条目也返回统一导出。登录、店铺采集支持同一停止信号；京东单次请求结束后完成导出再退出。
回归通过：真实业务停止于当前页第1条后仅导出该条，CSV/JSON真实写盘读回一致；任务保存完成前不关闭浏览器，保存错误不自动退出。
完整自检57通过、0失败、3跳过；验证发现停止时详情统计仍使用整页数，已改为实际处理条数，定向6项再次通过。此轮生产代码返工1次（日志统计）。
边界：等待在途网络请求结束可能需要几秒；操作系统强杀/点击窗口关闭按钮不承诺保存，使用说明已明确。

## 边界

不以额外确认框代替保存，不推翻用户既有直接退出习惯；不误关外部浏览器，不增加另一套采集业务真源。
