# 008 督办架构最佳实践调研

状态：首轮调研完成；账号权限与真实接口验收尚未进行。日期：2026-09-08。仅研究与笔记，不实施代码改造。

最新进展：第二轮直接HTTP核实已找到当前网页的员工开关接口定义；账号级验证仍缺可用授权。详见文末第二轮记录。

## 意图

跳出“浏览器白屏后怎么补救”，重新选择实现客服督办最简单、可靠、省维护的方式。允许替换旧架构，不新增永久并行真源，不以无头浏览器隐藏故障。重要结论至少用两个独立来源交叉核验。

## 背景与边界

- 用户反馈昨天可用、今天所有业务窗口白屏。初始空白页不是充分解释。
- 本次对话先前的独立无登录环境访问：一次登录页空白并超时45秒，随后两次显示登录页；仅能证明当时存在间歇性加载异常，不能确定生产白屏根因或宣称API后端正常。
- 不启动会发送企微提醒、修改客服接单开关的生产任务；不修改登录凭证、配置、业务状态，不开启外部回调，不发布服务，不发送供应商消息。
- 不牺牲现有人工/AI区分、首条未解决消息计时、责任归属、转接来源判断、排班保护与已存在绩效账本。
- 只读源代码与明确需要的文件；不扫描 node_modules/venv/.venv/build/dist 等非源代码目录。

## 已确认的代码事实

- `src/main.js`：后台仍先启动Chrome，再创建聊天/上班/下班页面并访问工作台。
- `src/features/transferMonitor/transferApiClient.js`：联系人、成员、消息已经走HTTP，但通过 `page.evaluate(fetch)` 执行，鉴权读 `localStorage.user.token`；是网页内部接口，不等于开放平台API。
- 联系人请求只有一次 `pageSize=100`，未实现翻页；尚不能证明拿到了平台所有联系人。已有说明书的“完整快照”不能替代接口验证。
- `src/features/missedReplyMonitor/missedReplyWorkflow/contactScan.js`：消息按批次轮转读取，提醒识别延迟与客户数、批大小和请求耗时有关。
- `src/features/offDutyClose/memberSettingsPage/view.js`、`rowReader.js`、`memberSwitch.js`：进入设置页、搜索成员、读DOM、点击开关；上班扫描还会刷新页面。
- `src/features/scheduleQuery/scheduleSheetFetcher.js`：金山排班也启动无头浏览器读取 `window.APP.workbook`，只移除客服浏览器仍不等于整个项目无浏览器。

## 最关键的新证据

公开文档的[开发建议](https://s.apifox.cn/db23f5b8-f331-4505-9d7e-e3b05560fdc2/doc-6951464)明确推荐接收事件更新本地会话数据，只在缺失时调用API补齐，并指出全部依靠查询可能受频率限制影响。

[小组级接口说明](https://s.apifox.cn/db23f5b8-f331-4505-9d7e-e3b05560fdc2/doc-6951463)：小组控制台提供“API接入”、调用凭证与开关；回调需要配置接收地址和对应回调开关。

注意：文档请求域名与项目服务同属 xiaoshunai.com，相关性很强；公开托管于Apifox，尚未通过当前账号后台的文档入口核实其发布归属、版本、套餐权限和当前账号可用性，不能据此宣称已完成官方API接入验证。

## 结论：成熟方案存在，但“所有需求已有现成开关”尚未成立

**推荐先核实平台原生督办/排班能力；缺失的自定义规则用官方事件推送 + 单一后台规则引擎实现。正常监控不依赖客服网页渲染。** 这是本次基于文档与代码的架构判断，不是已经实测可上线的结论。

成熟产品把这一类问题称为 SLA（服务响应时限）与工作流。Zendesk、Intercom 都提供回复时限及处理规则，但各自的起止语义不同：有的公开回复甚至自动回复会结束SLA。用户要求的“AI不结案、从首条未解决消息起算、弱收尾不清旧责任、不同人工回复类别”必须逐条验收。不能以“行业标准”之名改掉业务含义。[S1][S2]

原架构可实现功能，但不是这里最省维护的目标形态：已经有接口能力，却把网页加载和DOM放在关键业务路径中。改无头、加重试、直接把页面fetch搬到Node后继续高频扫全量，都没有充分利用平台已公布的事件能力。[S3][S4][S5] 这不意味着接口能修复供应商后端故障；它能消除网页脚本、渲染、选择器这一类依赖。

### 两个易误判的文档细节

1. 完整Schema比网页简化示例信息多：接收消息Schema确实有 `source` 与 `sendBy`，不能因为页面示例没展示就判定“不支持人工/AI区分”。历史接口的Schema和示例还存在 `data`对象/数组的不一致，需真实只读响应解决，不能加一堆猜测分支。
2. 关联企业级文档的示例服务器是 `test-aa-hub.ddregion.com` 测试环境，与有赞小组级 `zan-api.xiaoshunai.com` 不同。**本次没有向测试环境发送任何账号凭证或客户数据，也没有调用这些业务接口。** 企业级能力只能算相关产品线线索，正式环境和租户支持必须由后台入口或供应商确认。

## 最简方案的选择顺序

| 方案 | 维护成本判断 | 选择意见 |
| --- | --- | --- |
| 平台原生SLA/通知/排班路由 | 若业务等价且套餐可用，自有代码最少 | **先核实，满足就直接用。** 暂无证据证明小蟹能原生覆盖全部定制规则 |
| 正式API + 事件推送 + 小型单体服务 | 初次需凭证和可达的回调入口；之后无需盯浏览器 | **定制规则的首选目标。** 一个后台、一套规则、一份持久状态，GUI只展示 |
| 正式API增量轮询 | 不必接收公网请求，但受历史游标能力、延迟和限流约束 | 如果只能本机运行、没有可用回调入口，这是合理备选；不和回调双引擎并行 |
| 内部网页API + 浏览器授权 | 比DOM操作轻，但仍依赖非公开协议与网页登录 | 当前不作为终局；只有正式API明确无法满足时再评估，并说明剩余脆弱点 |
| 无头浏览器 / 更多重试 / AI视觉操作 | 仍要网页成功加载，增加隐藏状态或推理成本 | 不能作为本次换题答案 |
| n8n/大型工作流平台/消息集群 | 本项目的计时、责任归属仍需自定义，新增部署和另一处规则 | 当前没有必要；不因“成熟”就引入。不要默认Kafka、Redis、微服务、Kubernetes |
| 更换整套客服平台 | 可能得到原生SLA，但牵涉渠道、历史数据、使用习惯与费用 | 技术上开放考虑，现阶段证据不足以建议迁移采购 |

### 推荐目标的最小形态（设计判断，尚未实施）

`平台消息/分配事件 → 一个后台服务 → 同一套业务规则与截止时间 → 企微通知`

`GUI → 读取这个后台的状态和日志`

- 只有消息、分配、排班/状态变化才更新对应客户/成员。到期处理基于持久化的截止时间，不依赖不断重读聊天历史；进程重启重新读取未完成责任即可。
- 可选用一个SQLite文件保存事件去重标识、当前待办及通知结果；这是实现建议，不是要求另起数据库服务。现有绩效账本保持既有真源，任何替代迁移另行制定，不同时维护两套可写绩效账本。
- 源系统拥有消息、接待和员工状态；本程序只有按事件生成的必要工作状态，不建立第二套可手工编辑的客服主数据。API补齐与回调进入同一个归一化入口、同一个规则计算，不成为两套业务判断。
- 接收回调先校验来源并可靠落盘，再快速应答；后台处理。不要等待企微发送成功才回复上游。订阅最少必要事件、按事件/消息身份去重。富媒体后续补充是同一消息的更新，不能简单丢掉，也不能重新建责。[S6][S7][S18][S19][S22]
- 用户场景需要保留人工发出的消息：消息最佳实践中“过滤托管账号自己发的消息”是给自动回复机器人防循环的建议，**本督办不能照抄，否则看不到人工回复。** [S22]
- 小蟹文档明确会重试，连续失败还可能暂停回调30分钟；因此需要重启/中断后按已确认游标补齐，以及最后成功同步时间展示。这是供应商已说明的日常失败机制，非假想极端场景。[S6][S7]
- 不承诺网络通知严格“恰好一次”。本地去重可避免已确认事件重复执行，若发送超时但上游可能已收到，应标记结果待确认，而非无条件反复发送。
- 回调要求供应商能访问的接收地址；本机 `127.0.0.1` 不可作为云端供应商的回调目标。若已有可靠服务器可部署同一个单体服务，不预设新购云产品；若坚持本机且无接收条件，选择增量查询方案，不能偷偷加永久隧道服务。[S18][S19]

## 效率：能说什么、不能说什么

当前配置：转接扫描1.5秒，未回复扫描5秒，每轮20人；上班扫描5秒会刷新页面，下班扫描5分钟。共用聊天采集器已有价值，不应误说每个规则完全独立抓取。

按照读取代码推算，100个会话每轮20个，至少要5批才轮到一遍；理想5秒节奏约25秒，实际受网络串行耗时及保留待办增加影响。这是估算而非性能实测，且接口返回100条不证明平台总共仅100人。消息变化推送能消除对无变化客户的反复拉取，但具体CPU、内存、带宽与提醒延迟提升需要真实流量测量，不能宣称“快10倍”。

## 下一步验证关口（尚未执行，不等于调研没完成）

1. **查当前小组后台的API接入入口**：确认本文文档链接确属当前版本，API是否开通、调用凭证类型、有效期/轮换、价格/配额、企业级权限和正式域名。不要把网页Bearer token当成企业/小组级token。
2. **只读取小量真实响应**：消息历史、会话、成员，核对分页/游标、字段/时间戳、人工手机端/电脑端/AI标识及ID映射，不记录token或客户正文到issue。确认只读接口没有已读等副作用。
3. **确认业务等价**：先查原生SLA和工作时间是否能覆盖需求；若能，减少自建功能。员工在线状态/两个开关以及跨日排班保护必须明确；缺这些不能以“先做一半”宣称全项目替换完成。
4. **在已获授权的测试条件验收事件**：客户发言、人工实质/临时/标点回复、AI、弱收尾、明确解决、人工转接、系统分配、客服结束会话、重复/富媒体补充和补齐。回调没开通前只读研究无法证明投递正常，本轮不修改回调配置。
5. **决定运行位置后才设计落地**：已有服务器还是仅本机，决定推送或增量查询。可另行选择通知延迟验收目标，避免默认毫秒级要求。
6. **完整替换采集/执行边界**：实施时以确认过的协议重新设计一个客户端与一个规则入口；旧浏览器入口可恢复备份后退出生产，不长期双跑双发。迁移前校验既有待办和绩效数据，不靠兼容兜底掩盖缺字段。

### 给供应商的核实提纲（草稿，未发送）

- 本租户是否支持小组级消息/会话回调及历史API？请提供当前正式文档、正式域名、额度及凭证规则。
- `source/sendBy/isSelf`能否稳定区分AI、桌面人工、企微手机人工，并确定真实操作客服？是否需额外开通自身消息推送？
- 如何读取和修改每位客服的自动分配、可被转接状态？原生工作时间是否能直接保证班外不接单，能否支持每日轮班、休息和跨日？
- 历史消息/会话的保留期、游标方向、补齐与事件排序/去重协议是什么？小组回调如何验签？
