# 超时自动转接当班在线客服

## 最终口径（用户 2026-09-16 定稿，最朴素的版本）

> 用户原话：“简单的口径就是售前转售前，售后转售后，运营的接待算售前。无论是售前还是售后，只要有人在线就可以转，只不过硬规则是只转当班上线了的客服，否则转了没人回复。”
> “核心关键是客户的信息有人回复就这么简单。”

1. **触发**：首次超时 / 10 倍漏回复提醒到点，且**原接待已不在自己班次的时间窗内**（运营账号一律按不在班）。
   - 在班时间窗：早班 `08:00~16:30`；售前晚班 `15:45~23:45`；售后晚班 `14:00~22:30`。
   - 早晚班重叠期（售后 14:00~16:30、售前 15:45~16:30）里早班人还没下班，**不算不在班**。
2. **目标**：**同组**（售前→售前、售后→售后、运营→售前）+ **当天当班**（本人班次时间窗覆盖当前时刻）+ **已上线**（售前看「可被转接」，售后看「自动分配」），按排班表从上到下取第一个满足的。
3. **“在班但没上线”也算没人管**（用户 2026-09-16 追加）：“在班，但是没上线当然也算是没人管，直接转给当班在线的人就行”。
   - 判定顺序：过了自己班次时间 → 转；还在班内但接单开关关着（没登录小蟹/没开接单）→ 也转；还在班内且在线 → 不转。
   - 原接待的在线状态查不到（快照过期/缺人）时维持现状不转，避免误伤正在忙的人。
4. **交班补判**（用户 2026-09-16 追加）：“空档2要加，交接的时候容易出问题”。
   - 场景：客户在早班还在班时就提醒过、一直没人回，等早班下班后不会再有新提醒，客户会一直挂在下班的人名下。
   - 做法：主循环每 5 分钟对“真的分配到人 + 客户还在等回复”的会话补判一次（`autoTransferSweep.js`）；同一客户 30 分钟内最多真正处理一次，原接待换人可立刻重判；账本落在 `runtime/auto-transfer-sweep/state.json`。
   - 只在真正动手时记账（发出转接 或 触发@主管），普通“在班不转”不记，否则下班后就补判不到了。
5. **不看值班背景色、不看组长、不看值班标记**：排班表颜色只用于 `排班颜色清单` 诊断日志，不参与选人。
6. **当班的人都不可接**（都没上线 / 没人排这个班）→ **不转** 并 **@主管**；非工作时段不转也不发群。
7. **指令发出 ≠ 成功**：发 socket 帧后按联系人快照核对 `assignedTo` 真的变成目标才算成功，成功发群简报、失败@主管。

> 这条口径取代了此前基于“值班人（浅绿/浅蓝背景色、售后组长在班）”的选人规则——那些规则和用户真实需求（客户消息必须有人回）对齐度不够，已从代码中删除。

## 意图

运营/售前/售后负责接待的客户，在首次超时或 10 倍阈值漏回复时，若原接待已过自己的班次时间，自动把客户转给当前当班且在线的同组客服，避免客户长时间没人回复。

## 落地记录（2026-09-16）

**根因**：原实现走 `POST /api/chat/assign`，该路径从未存在（2026-09-16 09:19 实测 HTTP 404）→ 自动转接从未成功。平台把“分配会话”做成 **socket.io 事件**：页面只有一条 `wss://<域名>/ws/socket.io/`，上面挂 `/client`（聊天与分配）与 `/notify`（只收通知）两个命名空间，事件帧形如 `42/client,["assignChat",...]`；已用只读探针实测捕获真实帧。

**链路要点**：

- 判定与挑人：`src/features/timeoutAutoTransfer/timeoutAutoTransferPolicy.js`（`decideTimeoutAutoTransfer`、`listOnShiftGroupMembers`、`pickOnlineTarget`）。
- 发指令：`attemptTimeoutAutoTransfer` → `42/client,["assignChat",{chatId,groupId,assigneeId}]`。
- 核验：`autoTransferVerificationStore.js` 登记待核验，`workflowRunner.settlePendingAutoTransfers` 按联系人快照确认 `assignedTo`。
- 通知：`autoTransferNotifier.js`，成功发群简报、失败/无人可接 @主管。
- 在线依据：上班监控每轮发布的共享快照（`onlinePresenceSnapshotStore.js`，TTL 90 秒，覆盖当天全部排早/晚班的人），转接策略只读快照，不重复读页面。

## 回归记录（2026-09-18）：帧少了 `/client` 前缀 → 平台静默丢弃（山韵摄影）

**现象**：`已发送转接指令 ... 命名空间=默认` → 30 秒后 `转接未生效 assignment_unchanged`；交班补判再发一次 → `assignment_still_empty`；两次都@主管。
日志：`runtime/current-run.log:1328 / 1344 / 1372 / 1402`（详录见仓库根 `失败台账.md` 同日条目）。

**根因**：命名空间前缀是"发送时现扫最近 40 帧里的连接帧"猜出来的。页面 09:13 启动、09:46 才第一次转接，
连接帧 `40/client,...` 早被 engine.io 心跳（`3`）挤出 40 帧窗口 → 前缀算成空串 → 帧发到根命名空间，
服务端不跑 `/client` 的 `assignChat` 处理器 → 什么也没发生。
09-16 的两次"转接生效"都是页面刚打开几分钟内发的（临时脚本 `/Temp/auto-transfer-live-test.js`），
所以这条路径从没在"长跑页面"上验证过。

**改法**（`appSocketFrameProbe.js`）：
- 连接/事件帧一出现就把该 socket 的命名空间**永久记住**（`seenSocketIoNamespaces`，去重，不随排障用的 40 帧缓冲淘汰）；发送前缀只认这份记忆。
- **没有任何 socket.io 证据时拒绝发送**（`ok:false, reason=chat_namespace_unknown` → @主管），绝不再发无名帧当哑弹。
- 选 socket 时优先命中聊天命名空间，其次比帧数；发送拆成"读现场 → 定目标（纯函数）→ 发帧"，页面内外共用同一份帧正则（通过参数带进页面）。
- 测试：`npm test` **452/452 全绿**，含现场复现（40 帧全心跳仍必须发 `42/client,[...]`）、
  反向断言（无证据 → 一帧都不许发）、以及"不许回去扫最近 40 帧"的锁死断言。

**顺带查清（不是本条故障）**：二次失败报 `assignment_still_empty` 是平台自己在释放运营席位名下的会话——
`已分配` 09:46:55=10 → 09:47:00=9 → 09:48:54=2；当天 09:27:50 也有一次 12→4（同一现象、与转接无关）。
客户 09:49:54 被人工派给邓远祥、09:50:19 人工回「好的」，业务没漏客。
