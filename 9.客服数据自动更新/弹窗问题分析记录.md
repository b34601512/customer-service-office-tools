## 离线阅读得到的当前设计（待真实页面验证）

当前流程先确认登录态，再打开业绩页面，等待日期控件和自定义按钮出现，应用日期，持续读取页面是否完成加载并出现下载按钮，最后才进入下载流程。

这样设计是为了避免页面尚未准备好就操作日期或下载；但“优惠竞争力下降提醒”属于页面上的额外遮挡状态，当前流程没有统一处理这类业务弹窗。

这只是代码阅读结论，不是最终问题结论；必须等真实页面手工跑通后再确认弹窗出现的位置、时机和关闭动作。

完整程序路径是：连接已经打开的 Chrome → 确认登录和店铺 → 打开业绩页面 → 确认日期控件可用 → 应用日期 → 确认结果稳定 → 点击下载 → 等待文件并校验日期 → 保存文件 → 恢复人工下载目录 → 断开连接。

弹窗如果出现在“打开页面”到“点击下载”之间，就可能挡住日期操作或下载按钮；但目前还不能判断它应在哪个具体阶段处理，必须用真实页面确认。

现有程序已经有一个“平台安全提醒”统一检查和关闭流程，但它只针对安全提示、风控和滑块验证；截图中的优惠提醒不应直接混入该规则，除非真实页面证明它们属于同一类页面状态。

## 第一阶段结论

## 弹窗关闭的可复用规律（2026-08-18 自动运行验证）

本次答应当日全流程（汇总→金山同步→筛选→客服姓名确认）未遇到遮挡弹窗，
但全程各平台的“检查遮挡弹窗”步骤均由统一引擎 `src/shared/blockingPopupEngine.js` 自动执行。
结论：以后遇到新弹窗不需要每次都新写一套关闭技能，遵循以下规律即可。

可复用规律（单规则、多平台、不改业务）：

1. 弹窗统一特征是“一个可见的对话框 + 一个明确的关闭入口”，用一个引擎遍历处理。
2. 引擎只允许关闭**当前这个可见弹窗**的唯一明确关闭入口；
   候选关闭入口按通用白名单匹配（`[aria-label='Close'/'关闭']`、`.ant-modal-close`、
   `.el-dialog__headerbtn`、`.close`、文案“关闭/取消/知道了”等），口号是“只关当前弹窗，不点业务按钮”。
3. 判断“是否挡住流程”的时机统一：每次关键操作（应用日期、等结果、点下载等）前都执行一次弹窗检查。
4. 处理动作固定：读取该弹窗唯一容器 → 校验可见 → 只点击它的关闭入口 → 继续原流程，不改变任何业务数据。
5. 遇新平台新弹窗时：先真实页面取证（容器、关闭按钮、标题），若其关闭入口不在白名单内，
   只把**已取证的最小选择器**补进引擎白名单；不要为单个弹窗新建独立关闭模块。
6. 已取证特例：天猫“优惠竞争力下降提醒”= 容器 `div.ant-modal-wrap.high-price[role="dialog"]`，
   关闭按钮 `button.ant-modal-close[aria-label="Close"]`，属于业务提醒，只关不点“调整优惠”。
