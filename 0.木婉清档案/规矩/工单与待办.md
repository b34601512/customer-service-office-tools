## 六、工单与待办

- 待办表：《售后待办清单》（另有对应的《售前待办清单》）（只读查看时用口令「看售后有什么任务没完成」，文档链接/docid **不入库**）。
- **备注里已有处理动作（如「已通知拦截」「已发起协商」）= 已处理**：可帮勾「是否完成」，**不再跟催、不另开单**（黎路遥 2026-09-30）。为什么：客服已经动过手，再催一遍就是重复打扰，还会把已办的事重新翻出来。
- **自己的待办 / 要拍板的事 → 开 GitHub issue，一单一事**（黎路遥 2026-10-23 16:55：金山《木婉清 · 工作记录》已由他删除，「新的规则是开 GitHub issues 做记录」）。别再写回本地堆积、也别再建金山表；**一次只推一件**，做完就关单；今天的活今天完、卡住主动确认。
  - **唯一入口（2026-11-08 起）：`node 工具/待办.cjs "一句话" [--body-file 正文.md] [--repo 硅基公司|木婉清]`**——它开单并打印 `#号（一句话）`；断点里只许写这个 #号。别再手敲 `gh issue create`，两个入口就会出两套格式。
  - **两个仓库，同号不同事**：默认 `木婉清`（本仓 `b34601512/customer-service-office-tools`）；公司/跨岗的事用 `--repo 硅基公司`（`c34601512-cpu/silicon-company`）。**断点写 #号必须带仓库**：`#714（木）`／`#777（硅）`。为什么：两边都有 #714，不标仓库就会查到另一件事，判断依据直接错。
  - **同一个问题不许问第二次**（2026-11-05）：没答完的留在 issue 里写清「哪半已定、哪半还问」；他答完当场关单并把依据写进评论。

### 六之二、「文件」也是待办，别拿「它不是 issue」当理由（2026-10-26 黎路遥纠正）

**原话**：「那你为什么记得这件事情，待办事项不是应该上 issues 吗，做完就关闭，就不会明天又问我一次」。

**踩的坑**：未成交原因报表引擎 v1 是纪晓芙做的一份文件，我把它当「本地产出」放着没开单 → 第二天又拿它问老板「要不要发你看」。他其实 10-25 就看过了。

**落法**：

- 判据不是「这是不是一件活」，而是**「将来会不会让我再问一次」**——会，就先开 issue（哪怕只是「某份文件等人看一眼」）。
- 「做完」的标志不是文件存在，是**有回执、单子当天关掉**；关单评论写清谁在什么时候确认的。
- 本地只留指针（`#号（一句话）`），正文进 issue；这样「为什么记得这件事」永远有答案。
