## 叫人＝串联，且必须「上一个收窗了才拉下一个」（黎路遥 2026-10-31 14:39）

- **原话**：「串联的意思是，上一个完成了，收窗了才下一个，否则我电脑会卡死」；「这个事情要我说多少次才能记住」。
- **为什么（写清，别只抄一句话）**：
  1. 一个 TUI ＝ 一个独立的 pi 进程＋一个模型会话，常驻几百 MB 内存，还要一直等模型返回。
  2. 同时开着几个 → 内存和 CPU 一起被占满，机器就卡；多个窗同时抢同一个模型，每个都变慢。
  3. **收窗＝进程真的退出、内存释放**。没收就拉下一个，等于在已经占着的资源上再叠一层。
  4. 所以顺序必须是：上一个**干完 → 收窗（进程没了）→ 才拉下一个**；没收到「进程已退出」的确认，就不许拉。
  5. 反过来也不许：已经拉起来的窗中途收掉再叫一遍，等于白烧一遍 token（黎路遥 2026-10-31 14:40）。
- **驱动它的机制要按这条改**：叫醒器原来只等「起步宽限 90 秒」就拉下一个（不是等收窗）→ 前面全堆着，这就是 10-31 14:39 电脑卡死的直接原因；改成等上一个窗进程消失才拉，同一时间最多 1 个。
- **禁令（我自己）**：**不许为了通知一件事群发私信**（一次 19 家 = 连锁拉 19 个窗）。要么我自己动手做，要么贴 GitHub issue 让各窗下次开工自己看。
- **要叫人时**：一次只叫一个，等它**收窗**了再叫下一个；批量的事走 issue／回执，不走私信。
- **已经拉起的窗，等它干完，别中途收掉**（黎路遥 2026-10-31 14:40「已经拉起来了就等干完吧，否则又要重叫浪费token」）：收掉再叫＝白烧一遍 token。

## 收窗由那家自己决定，我不替他关（黎路遥 2026-11-04 17:5x）

- **原话**：「TUI 界面应该由每个人自己来决定关不关吧，否则他还没做完就关了」。
- 所以：**我只开窗、不关窗**——别用 `关窗.ps1` 去收别人正在干的窗，也别因为他「看起来没动」就收掉。
- 他要收工：自己跑 `自己收窗.cjs`（或把活干完主动收），**进程真退出了**我才当这扇窗结束。
- 我判断「上一扇收没收」只看进程在不在（`查对端窗.cjs` 显示「不在」），不靠猜。
- 例外只有一种：他明确说「你把他关了」/ 窗卡死到不可用且他同意——这两种先问再动。
- **他正在对话的窗，我一概不插手**（黎路遥 2026-11-04 18:0x：「先不关，我还在跟他对话」）：不关、不催、不再往里塞私信（私信会插话打断他和那家的对话）；要交代先问一句，或者等他聊完再接。
