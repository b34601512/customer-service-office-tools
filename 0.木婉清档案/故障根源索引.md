## 一、动手前的五个动作（顺序不能反）

| 步 | 做什么 | 卡住会怎样 |
|---|---|---|
| **0** | **先定义问题，不是先定位问题** | 跳过这步＝在旧设计上打补丁（军师原话：「会被过去的设计思想污染自己大脑」） |
| **1** | 问：**这一步是必须的吗？** 能不能换条更干净的路 | 不换路＝在错路上打磨（「钻头 vs 墙上的洞」） |
| **2** | **5 个为什么**，上一层的输出当下一层的输入 | 停在第二三层＝修的是症状 |
| **3** | 列出**全部**可能原因，排序，逐个排查 | 死盯一个＝第一个故事里「认定是键盘」 |
| **4** | **测试与观察**（日志/数据/报错），做选择题不做填空题 | 靠猜＝现象一次就下结论 |
| **5** | 修完问：**那个错还在不在**（不是「改对了没有」） | 不然就是「这次不发作」 |

**军师最狠那句**：
> 「你在一条错误的道路上你优化的再完美……不如直接换一条更干净的路。」
> ⭐ 我的记法：**修的是「让这个错不成立」，不是「修到它这次不发作」。**

## 三、实例（自己走一遍，模板照着填）

### 实例 1｜跟读进程越跑越多（2026-10-18，王语嫣报、老板 20:19 令）

```
① 现象：机器上同时跑着 3 个跟读进程，前两个父进程早已死（孤儿）。
② 这一步是必须的吗：监听是必须的；但「靠一个没人收的进程」不是必须的。
③ 5 个为什么：
   1. 为什么有 3 个 → 每次续窗/重启都新起一个
   2. 为什么旧的没退 → 父进程（窗口）结束时它成了孤儿，没人收
   3. 为什么没人收 → 没有「谁在跟」的登记，程序自己也不知道
   4. 为什么程序不知道 → **启动时从不检查有没有同类在跑**
   5. 为什么不检查 → 设计时假设「一个窗口一条链」，没考虑重启会留残骸
④ 归类：C 类（结构复发性）
⑤ 怎么证明那个「错」不在了：不是杀一遍。要能演示「再起一个 → 它自己退出」。
   实测：第二次启动打印「已有实例在跑（pid 54332）」并 exit 0 ✅
   反向断言：tests/跟读收件箱.test.js 两条（锁活着→挡住；锁死了→自愈放行）
```

**这次为什么不算小修小补**：杀进程只解决「现在有 3 个」；加锁解决「以后不会再长」。
**但仍有缺口**（诚实记账）：孤儿进程本身还在，锁只是让新的不来——父进程死后锁文件残留靠「pid 探活」自愈，已覆盖；**窗口被杀时锁不会被清，但因为探活，不影响下次启动**。

## 四、自检三条（判断自己是不是又在小修小补）

1. **同一个地方修过 3 次以上吗？** → 没找到根源，在打补丁。
2. **我的修复是「让它不自爆」还是「让它不需要那个兜底」？** → 前者是小修小补。
3. **一个从来没报过问题的监控，我敢不敢说它不是没在查？** → 不敢说 = 假安全。

军师原话对得上：
> 「我担心模型……**或用强制兜底、兼容和绕行掩盖设计错误。**」
> **「用兜底掩盖设计错误」＝小修小补的定义。**
