## 二、代码审读发现（4 条，均不改稿）

### A）⚠️ 阻塞级：Windows 下带空格的任务被拆参
- 位置：`派活.cjs` L129-133，`要壳 = win32 && /\.(cmd|bat)$/` → `spawnSync(cli, 参数, {shell:true})`；Node 把参数直接拼接、**不加引号**。
- 本机 `where codebuddy`＝`…\npm\codebuddy`＋`codebuddy.cmd`；复刻脚本查找逻辑（PATHEXT 顺序）命中 **`codebuddy.cmd`** ⇒ **Windows 上每次真派活都走这条 shell 分支**（不是理论路径）。
- 实锤 argv：`["…\fake.js","-p","统计","当前","目录","md","文件","--model","deepseek-v4.1-flash",…]` —— `-p` 只拿到第一个词，CLI 拿到的任务是残的。
- 影响：README/清单自己的示例「统计当前目录下所有 md 文件的字数，列个表」就带空格；AI 窗口写的任务描述几乎必带空格 ⇒ 该工具在 Windows 上核心功能不可用。
- 修法建议：别用 `shell:true` 拼串；改 `process.execPath`＋CLI 的 JS 入口（npm-shim 的 .cmd 里能看到入口；脚本已有兜底搜索 `@tencent-ai/codebuddy-code/bin` 的分支可复用），或对参数做 cmd 转义。修完建议补一条「带空格任务 argv 不被拆」的反向断言测试。

### B）契约级：单对象 JSON 不解析
- 位置：L162 解析循环只有 `if (Array.isArray(数据))`；else 只把 stdout 塞进「错误文本」，L180 的纯文本兜底又因「数据是真值」不触发 ⇒ 单对象输出一律 exit 5。
- 与 README §台阶2「也可能是单个对象…」、清单 B「两种 JSON 形态都能解（数组 / 单对象）」直接不符。
- 修法：非数组对象当成 `[数据]` 处理即可（或改文档降级声称）。

### C）契约级：额度判定被 `!回复文本` 遮蔽
- 位置：L194 `含(错误文本,[额度词…]) && !回复文本`。当 CLI 把额度报错放在 `result` 且 `is_error:true` 时，`回复文本` 已被填上 ⇒ 条件不成立 ⇒ 归 5（实测 exit **5**，stdout=Insufficient credit…）；只有「额度词仅 stderr/无 result 文本」才归 2（实测 ✓）。
- 影响：若真实额度耗尽走 `is_error`-result 形态，调用方会按 5「重试一次」而不是按 2「直接回落」——违反本包核心合同（2 与 5 必须分清）。真实额度耗尽形态未验（不能为它真烧光额度），但 README 自己就在教 `is_error` 解析，该形态很现实。
- 修法建议：额度判定改为「命中关键词 且（无回复文本 **或** `元.is_error`）」，同时保留「正文偶然含词但有正常回复」的防误判。

### D）文档级：「message 覆盖文本」不成立
- README §台阶2 称「本包：`message` 覆盖文本」；代码是按数组顺序后者覆盖（L166-176 无优先级策略）。实测 `[message,result]` → 取 **result**（result 在后则 result 赢）。真实 CLI 数组里 result 通常在最后 ⇒ 实际是 result 生效。
- 修法：实现真优先级（如 message 永远赢），或把这句改准。
