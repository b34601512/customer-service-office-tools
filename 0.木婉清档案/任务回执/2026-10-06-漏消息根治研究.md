## 一、官方口径（企微开发者文档，2026-10-06 现场抓取）

文档地址：<https://developer.work.weixin.qq.com/document/path/101463>（《智能机器人长连接》，页面标注「最后更新：2026/05/25」，本次 curl 200）。

### 1) 连接唯一性 —— 官方明说 【官方】
> **连接数量限制**：每个智能机器人同一时间只能保持一个有效的长连接。当同一个机器人发起新的连接请求并完成订阅（aibot_subscribe）时，新连接会踢掉旧连接，旧连接将被服务端主动断开。
> 注意：
> - 开发者需要在业务层面避免同一机器人建立多个长连接
> - 如果需要实现高可用，建议采用主备切换模式而非同时多连接
> - 旧连接被踢掉时，开发者会收到连接断开事件

同页还给了**断开事件**的官方格式：
> 连接断开事件 `disconnected_event`：当有新连接建立时，系统会给旧连接发送该事件并且主动断开旧连接
> （JSON 示例：`cmd=aibot_event_callback`，`body.event.eventtype=disconnected_event`）

### 2) 重试 / 补推 —— 官方没有给长连接补推机制 【官方】
- 101463 全文**没有**「消息重试 / 补发 / 补推 / 离线消息」章节；唯一带「重传」的是上传临时素材的「断线重传」（素材分片，不关消息）。
- 长连接收消息流程里**没有客户端 ACK 环节**（SDK 收到 `aibot_msg_callback` 后直接分发，不回执），所以不存在"没回执→服务端重发"的机制。
- 有重试的是**另一种模式**（设置接收消息 URL / Webhook）——文档 <https://developer.work.weixin.qq.com/document/path/90930>《回调配置》原文：
> 企业微信服务器在五秒内收不到响应会断掉连接，并且重新发起请求，**总共重试三次**。（仅针对网络连接失败或者网络请求超时情况重试……）**目前无法保证 100% 回调成功**……建议开发者不要强依赖回调，需要额外机制对齐相关业务数据。
- 注意：长连接与 Webhook 是**互斥的二选一**（101463 原文：「API 模式只能选择一种方式……切换到『设置接收消息回调地址』模式会导致现有长连接失效」），所以不能靠切 Webhook 拿到那 3 次重试。

### 3) 主动拉取历史消息的接口 —— 智能机器人没有；只有另一套「会话内容存档」体系 【官方】
- 101463 没有任何历史消息拉取 API；SDK 也没有。
- 官方能"拉历史"的只有 **会话内容存档 / 数据与智能专区**：
  - 《使用前帮助》<https://developer.work.weixin.qq.com/document/path/91361>：要在**管理后台开启会话内容存档**（先设范围、IP、消息加密公钥），员工需被告知；与外部联系人的会话还需对方同意。
  - 专区程序 SDK《获取会话记录》<https://developer.work.weixin.qq.com/document/path/99968>：游标增量拉取（`has_more`/`next_cursor`/`msg_list` 按时间升序），字段里**明确有 `sender.type=3 机器人`**，即理论上能拉到机器人参与的会话。
  - 它是「数据与智能专区」的一整套独立工程（专区部署+公钥+合规），**不是给智能机器人长连接用的补拉通道**。
- 顺带排除一个误会：《获取群聊会话》<https://developer.work.weixin.qq.com/document/path/101028> 原文是「查询通过**智能表格自动化创建的群聊信息**」（群名/群主/群成员），**不是消息历史**。

## 二、本机 SDK 行为（证据在代码/日志里）

- 用的 SDK：`@wecom/aibot-node-sdk` **1.0.7**（`27.企业微信机器人/package.json` 依赖 `^1.0.7`，node_modules 实装 1.0.7）；守护 `scripts/长连接守护.js`。
- **被顶掉时能不能感知：能，但只有"标准被踢"能看到。** 【实测】
  - SDK 代码（`node_modules/@wecom/aibot-node-sdk/dist/index.cjs.js` 383~397 行）：收到 `disconnected_event` → 打 WARN「Received disconnected_event: a new connection has been established…」→ 停止心跳、清待发消息、`isManualClose = true` → `emit('disconnected', reason)`（reason=`New connection established, server disconnected this connection`）→ 关掉 socket。
  - 守护 `scripts/长连接守护.js` 135 行确实监听了：`client.on("disconnected", () => log("连接断开（SDK 会自动重连）"))`——**文案是错的**：被踢这一支恰恰**不会**重连（见下）。
- **重连行为** 【实测（读代码）】：
  - 普通断线：指数退避 1s→2s→4s→……→ 上限 30s，`maxReconnectAttempts` 默认 **10 次**（10 次用完 → 发 `WSReconnectExhaustedError` 到 `error` 事件 → **放弃，不再重试**）。心跳默认 30s 一次，连续 2 次没收到 pong 判连接已死 → terminate → 走重连。
  - **被踢（disconnected_event）：不重连。** 代码注释原话：「disconnected_event（被踢下线）不会触发重连，因为 isManualClose 已被设为 true。」→ 也就是说：真被踢一次，守护进程还活着、但**永久失聪，直到有人重启它**（本机目前没有这个看门狗）。
  - 重连成功后**不会补消息**（代码里没有补拉逻辑；官方也没这个机制）。
- **10-06 当天的实况比"被顶"更微妙（重要）** 【实测】：
  - `grep` 全量 `.state/daemon.log`：从 10-05 08:44:39「认证并订阅成功」以后，**到 10-06 16:00 没有任何断开/认证/WARN 行**——当天本机**没收到 disconnected_event**，连接没有被服务端断开。
  - 但当天 **群消息 0 条**（首条群消息 15:28:57），而**单聊一直正常**（09:34 起持续收到）；「别的 AI 停掉后」群消息立刻恢复。消息按天计数（`.state/inbox.jsonl`）：10-05 group=5 / 10-06 group=7（全在 15:28 以后）。
  - 结论【推测】：当天不是标准"被踢断线"（否则会有事件、单聊也会断），而更像**多连接/路由层面的静默失效**（单聊路由在、群路由不在）——社区里有人报过一模一样的现象（见下 §三-2）。**这意味着只监听「被顶事件」不够，必须有独立于 SDK 事件的活性检测。**

## 三、别人遇到过吗（GitHub，官方仓库 + 社区主流实现）

1. **【社区】WecomTeam/wecom-openclaw-plugin #54（open）+ #55（closed 修复）** —— 官方团队的插件仓库，标题就是 *Reconnect when WeCom WS sends `disconnected_event`*：
   <https://github.com/WecomTeam/wecom-openclaw-plugin/issues/54> 、<https://github.com/WecomTeam/wecom-openclaw-plugin/pull/55>
   - 结论：收到 `disconnected_event` 后如果只当作普通帧丢掉，会出现「**half-alive：心跳 ack 还成功、进程看起来在线、新消息不再进来**」；`@wecom/aibot-node-sdk` 只在传输层断开/心跳判死时自动重连，**不会**因逻辑踢下线重连；修法 = 收到该事件后**主动轮换连接**（带冷却，防抖）。
2. **【社区】NousResearch/hermes-agent #58649** —— *WeCom callback watchdog blind spot: DM messages keep watchdog fed while group messages silently dropped*：
   <https://github.com/NousResearch/hermes-agent/issues/58649>
   - 结论：**重连之后，服务端可能恢复了单聊（DM）回调、但群体（group）回调一直不恢复**；一个"收到任何消息就刷新"的看门狗会被单聊喂饱，永远发现不了群消息在丢。→ 与 10-06 现象高度一致；正确做法是**群/单聊分别计时**。
3. **【社区】go-sphere/wecom-aibot-go-sdk #2（closed）** —— *修复 disconnected_event 导致 nil pointer dereference panic*：
   <https://github.com/go-sphere/wecom-aibot-go-sdk/pull/2>
   - 结论：文中直接写明「**当多个服务实例使用相同 BotID+Secret 连接企微时，新连接建立后旧连接收到 `disconnected_event` 被踢**」——第三方 SDK 同样按"会踢"实现，且这个场景真实常见到有人踩出崩溃 bug。
4. 备注（同关键词、不同根因）：`WecomTeam/aibot-node-sdk` #19「接收不到群消息，只能接收到私聊消息」(已关) — <https://github.com/WecomTeam/aibot-node-sdk/issues/19>：结论是**群聊里必须 @机器人**才会推，不 @ 收不到（不是被顶）。另有 hermes #47564/#92804：`errcode 846609（aibot websocket not subscribed）` 的"假在线"死窗口，57~79 秒内的消息静默丢——属于**发送侧**的同类"连接在、订阅没了"问题，供后续参考。

## 四、根治方案候选（本轮只出方案，不动手）

### A. 单连接唯一（已做一半）——还差什么
- 现状：官方要求业务层自己避免多连接；10-06 已拍板**身份独享**；开机自启已有（启动文件夹「木婉清-企微守护」）；`daemon_entry.cjs` 用 PID 文件防同一目录重复开。
- 缺口：
  1. **无自愈**：被踢/10 次重连耗尽后不用重启就永久失聪（SDK 不重连被踢支）；启动文件夹只在开机时拉一次。
  2. **凭据可复制**：`project-config/aibot-credentials.local.json` 和 wecom-cli 本机凭据库（`~/.config/wecom/`）都是"谁拿到谁能连"；官方文档**没有**设备白名单/单点绑定这类能力。
  3. **看不见别人**：本机无法查询"当前有几条连接"，只能被动等 disconnected_event（而 10-06 连事件都没有）。
  4. 本机排查：全仓库只有 27号 引用该凭据文件（`grep aibot-credentials` 仅命中 27号 3 个文件）；程灵素用的是**另一个** botId（`aibqBJ…`≠木婉清 `aibRy5…`）；赵敏旧快捷方式指向的 `00.赵敏工作区/企微` 已不存在。→ 本机暂时干净，风险在外机/外部工具。
- 补法（低成本）：① 被踢后**允许自动重连**（身份独享下安全）+ 冷却；② 给凭据文件收紧 ACL、不要拷到别的仓库/机器；③ 守护加定时看门狗（见 B）；④ 怀疑外泄时**换 Secret**（后台操作，属运营/管理员动作，需黎路遥确认；"换完能否立刻踢掉已建长连接"官方文档没写，标**未证实**）。
- 可行性/成本/风险：可行性高 / 成本低 / 风险低（注意重连时别和别的连接打乒乓——身份独享前提下无此人）。

### B. 顶掉检测 + 告警（推荐 P0）
- 做法：
  1. 标准被踢：监听 SDK `disconnected` 的 **reason**，WARN 即告警（顺带把守护那句错误文案改掉）。
  2. 静默失效：**群/单聊分开计时**（像 hermes #58649 的教训）＋工作时间阈值（如营业时段 > 90~120 分钟无群回调 @ 记录就进入"可疑"）；再加一个**主动自检**（定时 `守护:自检` 或重启守护探头）。
  3. 告警通道要**独立于木婉清自己**（它病了自己报不了）：本机弹窗/日志 + 既有的 **22号 webhook 群机器人**（`22.后台售后服务单分析/src/tools/send-wecom-notice.js` 在，webhook 与长连接是两条链路）；发告警短信/私聊属"真实发送"，内容与开关先请黎路遥拍板。
  4. 可选：异常时**自动重启守护**（身份独享下安全；重启后 15 秒内恢复）。
- 可行性/成本/风险：可行性高 / 成本低（一个巡检循环或小程序）/ 风险=误报（阈值可调），以及"自动发送告警"需先获得授权。
- **建议优先级：P0（唯一能兜住"静默失效"的一层）。**

### C. 定期对账补拉（先泼冷水：企微补不了）
- 智能机器人长连接**没有官方历史消息接口**——=> **技术上无法"把漏的补进来"**。
- 澄清任务书里的前情：`0.木婉清档案/任务/2026-10-05-完整聊天记录接口.md` 找到的 `GET /api/im/agent-trace/get-chat-list` 是**探域平台**的「买家会话完整记录」接口，**与企微群消息无关，不能用来补企微的漏消息**（它是买家↔客服AI的会话，不是金牌组群里人和机器人的消息）。
- 官方唯一可"拉历史"的是**会话内容存档/数据与智能专区**（§一-3）：要素=管理后台开通+范围/IP/公钥、员工告知、专区程序部署、cursor 增量拉取（含机器人身份消息）。可行性：**低**（重、要后台/合规/费用）；成本高；风险=隐私合规。→ **除非公司本来就要上会话存档合规，否则不建议为"补漏"上这套。**
- 现实可行的"对账"：人工兜底流程——① 漏消息后按截图补办（这次就是这么办的）；② 收工时/次日开工在群里请人确认"有没有@木婉清没被理的消息"；③ 把"每天早上自检时问一句"写进监听窗的开工自检。成本≈0，稳定，但依赖人。
- 可行性/成本/风险：官方通道低/高/合规；人工通道高/≈0/靠人。

### D. 其他
- **主备切换（官方建议的高可用方式）**：两条长连接不能并存，只能"备用待命、主挂了再顶"。需要外部协调（心跳租约/文件锁）且要防抢连，**复杂度高**，暂不建议；如要做，先做 B，再看有没有必要。
- **多机器人分流**：群消息只推给**被 @的那个机器人**，兄弟机器人看不到 @木婉清的发言，**兜不了底**；但**另一个机器人身份可以做告警通道**（B 的一部分）。
- **切 Webhook 短连接**：有"5 秒/重试 3 次"，但切换会先废掉现有长连接、需要公网 URL、服务挂了也一样丢——不是根治。
- **Secret 轮换**：疑似别人还持有凭据时最快的"断路"手段（需后台操作+通知使用者）；对已建立连接的即时性**未证实**。
